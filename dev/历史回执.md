## 批次 1b · 制作任务链诊断与自动续跑（本地已落地，待发版）

用户反馈：「合成一个音频后就停住，不会接着进下一批；关掉软件再打开，不知道任务是跑还是停，
希望队列里有在跑的任务就自动开始跑」。查完链路，真实状态如下。

**代码事实（不是猜测）**
1. `Producer.start` 一次只接一本书 + 一组 `onlyChapters`，`run()` 把这些章的所有段
   **拼成一个 WAV** 后注册一条成品，然后 `_state = "完成"` 就停。全工程没有任务队列，
   也没有「做完后自动接下一个」的调度器。所以「愣住、不知道后面进哪张」是真实缺口。
2. `TingbenApp.onCreate → Producer.restore()` 把 `running` 改成 `interrupted`，
   状态文案明确写「点「继续制作」接着做」；`ProduceService` 是 `START_NOT_STICKY`，
   进程被杀后系统不会重启服务。**打开软件一定是静止等待手动点**，既不跑也不说清在等什么。
3. 顺带查出一个真缺陷：`Producer.stop()` 只把 stopped 写进文件，没同步内存里的 `current`；
   `finally` 会按 `running` 再标一次 `interrupted`。结果用户主动停止的任务，
   下次开软件会被当成崩溃中断。自动续跑上线前必须先修，否则违背用户意图。
4. 批次 1 改了 TXT 切章规则，旧任务按旧章号存 `only`；`realProgress` 现在按新规则重算，
   旧任务直接续跑会把断点对错章。自动续跑必须能识别旧口径。

**本轮本地落地**
- 修 `stop()`：同步回写 `current = stopped`，finally 不再误标 interrupted
- `finally` 保留真实失败 stage（没完成 / 出错了 / 已停止），供守卫区分
- `TaskInfo` 加 `splitRule`，`TaskResume.SPLIT_RULE = 2`；旧记录缺省为 1，不自动续跑
- 新增 `TaskResume.autoResumeBlockReason` 与 `Producer.autoResume`：
  只放行「进程被杀 / 崩溃」留下的 interrupted 任务；手动停止、失败、旧切章口径、
  书被删、模型没齐、调音改过一律不自动跑，并给出可见原因
- 触发点放在 `App()` 的 `LaunchedEffect(Unit)`（Activity 可见之后），
  **不在 `Application.onCreate`**，避开 Android 12+ 后台启动前台服务限制
- 新增 `scripts/r127_verify.py` 并挂 CI，正向 23 条 / 旧形态 2 条 / 反向注入 13 例全拦下

**本轮不做（留给下一批次）**：任务队列调度器。理由见下。

### 下一批次的设计口径（工程判断，已按纠正后的来）

保留「一次任务 = 一本书 + 选中章 → 一个合并 WAV」的现状，**不改成每章出一个音频**：
那样会动 `AudioLibrary` 索引、章起点 JSON、断点指纹，牵连整条播放与续跑链，
且与后面的播放器统一耦合，改错代价太大。

队列 = 多本书 / 多批选中章的待做列表，复用现成的 `tasks.json`，加 `queued` 状态：
- 一个 `done` 之后调度器自动 `start` 下一个，不再停在「做好了」
- 界面明确「队列 N 个 · 正在第 M 个 · 做完后自动接下一个」，把「愣住」变成有反馈
- 调度器复用本轮同一套守卫，守卫不过就停队列并说清原因，不无限重试
- 用户点停止 = 暂停整个队列，不是只停当前一个，避免停了又自动跑下一个
- 失败（存储不足 / 引擎报错）即停队列并高亮，不自动跳过

**验证边界**：沙盒无 Android SDK，本轮未真编译；自动续跑与前台服务的实际时序、
旧任务守卫在真机上的表现，都要等出包后上手确认。

## 批次 1c · 分段看台灰格状态重建（本地已落地，待发版）

用户反馈：「生成这一章时看台已经切块成很多小节，未合成的灰色小块本来有显示；

**诊断结论：不是合成链路断了，恰恰相反，磁盘链路是好的。**
用户那句「继续合成还能按原来顺序」就是证据——分段计划、断点、逐段落盘都没丢。
坏的是**看台列表的数据源**：`ProgressScreen` 里 `segs` 有两个互斥来源。

| 来源 | 内容 | 何时生效 |
|---|---|---|
| `fallbackSegs`（`Workbench.segments`） | 计划段全量，含未合成的灰格 | `treeChapter == null`，进页面瞬间 |

`treeChapter` 是异步赋值，页面生命周期内两个来源发生切换：
先看全段（灰+绿）→ 加载完只剩已合成的 → 之后每合成一段 `st.done` 变化、
`LaunchedEffect` 重跑、树里多一条，UI 就多一个格子。
「切出去再回来」把 `remember` 重建，把这个切换暴露得更明显。
音频树里根本没有「还没合成」的段，拿它当列表来源，灰格必然整片不存在。

**本轮本地落地**
- `ProgressScreen`：`plannedSegs` 做唯一骨架，段数恒定；
  `treeWav` 只按 `seq - 1` 给对应段补 `wav`，决定绿/灰，不决定列表长度；
  `index` 统一重编号。删除 `chapterRows` 直接当 `segs` 的分支。
- 连带修正：章视角进度条分母原来是「已登记小块数」，随合成一起涨，
  百分比失真；改后分母固定为计划段数，进度才真实。
- `Workbench.segments`：去掉 `mapped.take(60)` 与 `coerceAtMost(59)` 硬砍
  （用户说「很多个小块」，超过 60 就显示不全）；兜底分支只留 2000 的极端保险。
- `r119_verify.py` 两条绑死旧形态的断言语义化；新增 `r128_verify.py` 挂 CI，
  正向 11 条 / 旧形态 5 条 / 反向注入 12 例全拦下。

**顺带查出、本轮不动**
`SegPlan.writeMap` 全工程没有调用点，`readMap` 恒为 null，
看台实际一直走 `Workbench.segments` 的兜底推算分支（按 `t.total` + 已落盘最大序号）。
启用 segmap 会改变续跑指纹口径，牵连 `realProgress`，不在这轮动，排到后续。

**验证边界**：沙盒无 Android SDK，本轮未真编译；
「切出去 / 切回来」在真机上是 Activity 重建还是仅重组、异步树加载的时序，
都还没上手确认。段数极多时看台用 `Column + chunked(8)` 全量渲染会变重，也待真机验。

## 批次 5 · 统一多选态（本地已落地，待发版）

## 批次 B · 章节表与分章链路（本地已落地，待发版）

对应整体问题清单 P1 第 4/5/6 条、以及 TXT 分章这条任务。本轮**纯本地推进**：

### B1 编码与 BOM 前置（`Importer.plainToText` 重写）

1.1.2 只数 U+FFFD 再试 GB18030/GBK/Big5。实测 Windows 记事本「Unicode」另存的
UTF-16LE 会被误选成 GB18030（替换符 1203 → 2），返回一串带 NUL 的乱码，
被 `BookStore.add` 用 `writeText` 永久写进书架，正则一个都匹配不上 → 整本 1 章。

现在把编码当独立阶段：BOM 优先于一切统计（UTF-8 / UTF-16LE、BE / UTF-32LE、BE），
UTF-8 BOM 跳过 3 字节；无 BOM 时先严格 UTF-8 解码（非法序列直接判失败，不再静默替换）；
再按中文密度打分选 GB18030 / Big5 / UTF-16。导入 Toast 也补上 TXT 章数
（`Result.chapterCount` 之前定义了但全仓没人读）。

### B2 规则集自动选优（`TocRules.kt` 新增）

参考成熟开源阅读器的做法，把「一套固定正则硬筛」换成多条候选规则 →
对这一本书统计有效命中数自动选优 → 目录页过滤 → 无命中按字数兜底。

- 7 条规则：常规中文 `第N章`（含站外常见的 `正文 第N章` 前缀）、卷、`1. 标题`、
  中文数字 `一、标题`、`Chapter N`、楔子/序章等特殊章、包裹符形态
- 抗误报：独占一行、只允许 ASCII 缩进（全角空格缩进视为正文）、标题长度 <= 35、
  不以句末标点结尾、负向断言排除「第三部分 / 第三节课 / 集合」类计数词歧义
- 目录页：连续标题行之间只有 1 个换行才成簇，整簇丢弃；正文第一章前面有空行/分隔行，
  换行数 >= 2，不会被一起吞掉。另有一层同名标题去重兜底
- 规则全不命中时按约 8000 字在最近换行处分节，**不再退回整本 1 章**

用仓库里的真实正则跑整书样本：带前置目录页的 5 种格式（第X章 / 正文 第X章 /
中文数字 / 纯数字 / Chapter N）全部恰好 6 章；完全无标题的书走字数兜底。
EPUB 仍走 `CHAPTER_SEP` 结构化分隔，一个字没动。

### B3 章节表落盘（`ChapterPlan.kt` 新增）

1.1.2 里 `ChapterSplitter.split()` 被 4 个地方各自重算，而音频索引、断点、
阅读位置全按章 index 存。规则一改章号就漂，已生成音频会整体对错章。

现在一本书一份 `books/{id}.chapters.json`，存 schema / ruleId / sha / chapters。
四个调用点（目录页、制作准备页、制作运行、断点校验）统一走 `ChapterPlan.resolve`。

**老书兼容**：1.1.2 的用户升级后，已有成品或任务的书首次打开会自动锁定
`legacy_v2` 规则（把旧启发式整套保留下来），章号与旧数据完全一致；
新书才用规则集自动选优。只有用户显式「重新分章」才换规则，
目录页会先预览章数与头尾标题，并明确提示章号会变、已做好的音频需要重做。

### B4 删书全量清理 + 旧断点迁移

## 批次 C · 主线程、内存与前台服务时序（本地已落地，待发版）

对应整体问题清单 P2 第 7/8/9/10 条。本轮**纯本地推进**：没推 main、没打包、
没升版本，`version.txt` 仍是 `1.1.2`。

### C1 制作准备页组合期同步读整本 + 切块

`ProduceScreen` 原来是 `remember(book, refresh) { ChapterPlan.resolve(c, it) }`，
主线程读整本再切块。现在与目录页同一套口径：`LaunchedEffect` + `withContext(Dispatchers.IO)`
一次性算出 `ProduceLoad`（书 / 章节 / 分块 / 上次任务配置），加载中给进度圈，
失败给中文原因。断点检查 `Producer.hasProgress` 也切 IO。

连带把三处 `BookStore.add` 的写盘切到 IO：导入（原来在 `withContext(Dispatchers.Main)`
里同步写整本）、分享、粘贴。Toast 与状态更新仍回主线程。

### C2 「清理分段音频」遍历删盘

`work.walkTopDown()` 原来在按钮回调同步跑，分段多时卡界面。
改成 `rememberCoroutineScope` + `withContext(Dispatchers.IO)`，回来再弹 Toast。

### C3 文本字符数上限

`Importer` 的 64MB 是**字节**上限；中文 UTF-8 一个字 3 字节，64MB ≈ 2100 万字，
JVM 里 String 是 UTF-16（约 42MB），再叠加切块列表与正则候选很容易 OOM。

新增 `BookStore.MAX_TEXT_CHARS = 6_000_000`（600 万字符 ≈ UTF-16 11.4MB、
约 1.4 万段，安全）。三道闸门：`BookStore.add`（含粘贴/分享入口）、`Importer.checkText`
（EPUB 与 TXT 都查，在读文件阶段就拦）、`ChapterPlan.resolve`（旧超大书兜底）。
三处 UI 入口都把中文原因 Toast 出来，不再直接崩。目录页与制作准备页的加载
也加了错误态，超长书会显示原因而不是白屏。

### C4 自动续跑的前台服务时序（两处纠正）

- **时序**：`LaunchedEffect(Unit)` 一进组合就跑，但组合完成 ≠ 窗口可见，
  Android 12+ 会拦「后台启动前台服务」。现在用 `LocalLifecycleOwner` +
  `LifecycleEventObserver` 等真正的 `ON_RESUME`，再 `snapshotFlow` 放行 `autoResume`。
- **失败不再静默**：`ProduceService.begin()` 原来 catch 掉异常后注释写「任务仍在
  内存协程里跑」——没有前台服务，进程随时被杀，界面却一直显示在制作。
  现在 `begin` 返回 `Boolean`；失败时 `Producer` 把任务停在「没开始」、
  写回 `stopped`（不会被下次当成崩溃中断自动跑）、给出中文原因，
  `autoResume` 把它作为 toast 透出。队列里的任务会被放回队列并暂停，不吞掉。
  服务内部 `startForeground` 失败也停自己 + 停制作，避免系统判 ANR。

### F0 查证「包里掺了给开发者看的代码」

### F1 输入朗读 / 播放器的「返回不知道回哪」

查到真因：`inputReadOpen` 和 `playerOpen` 都是**覆盖式浮层**，不进 Screen 枚举、
不进 nav 栈，却没有任何自己的 BackHandler。按系统返回键时，全局
`goBack()` 把**底层页面**切走了，浮层还盖在屏幕上；或者底层是根级页时
`canGoBack` 为 false，返回键干脆没反应 —— 就是用户说不清楚的那个现象。

修法：两个浮层各补一条 `BackHandler`，且注册在全局返回之后（Compose 后注册优先），
两层不打架。顺带把输入朗读顶栏的字符 `‹` 换成代码画的 `IconBack`、
热区从 20sp 字扩到 44dp，并补一枚「关闭」按钮。**全屏播放器同样中招，一起修了**
（这是查证时自己发现的关联缺陷，用户只提了输入朗读）。
