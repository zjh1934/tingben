## 1. 为什么做这一页

P4 性能二期（R79）出包后，队列里 P4b 是可选、P6 未定义。用户早先在「新软件要有什么」里点名过
「音频管理页要怎么设计」，而 7 张真机截图里这一页是最薄的：整屏只有「还没有音频」一张卡。
R75 只补了一句说明文案，没给下一步动作 —— 本轮插队把这一页的欠账销掉。

## 3. 终版形态

- **空态**：主卡 + 一句说明 + `去书架 ›` / `去看模型 ›` 两个可点文字入口。
  跳模型页时先写 `modelsFrom = Screen.AUDIO`，返回仍回本页，不乱跳。
- **有数据默认**：首屏只有一行汇总「共 N 个音频 · 合计 mm:ss」（右侧 `播放控制 ›`）+
  列表 + 底部跨页悬浮条。**零播放卡**，曲名与状态只在悬浮条出现一次。
- **展开控制**：点汇总行右侧才出详细控制卡，5 项功能一个不丢，默认 `mutableStateOf(false)`。
- **列表行**：只留一个实心主按钮（`试听/暂停/继续`），`保存到手机`、`删除` 降为小号文字按钮；
  `CreateDocument` 导出与 `AudioLibrary.remove` 一行未动。
- **汇总耗时**：`items.sumOf { AudioLibrary.durationMsOfBytes(it.bytes) }`，用 index 里已有的字节数，
  **零新增磁盘访问**（沿用 R79 的 `durationMsOfBytes`）。

## 7. 如实限定

- **真机仍是零证据**：交付的是代码与断言，不宣称「更好用」；按新纪律不向用户索取装机验证。
- 空态的「去看模型 ›」只是入口，模型缺件时仍不会凭空出声；它解决的是「下一步在哪」。
- 汇总「合计时长」按 WAV 24kHz/16bit/mono 由字节数推算，是估算值，不是解码实测。
- 播放控制展开态仍会与悬浮条同时显示曲名 —— 那是用户主动点开的详细控制，不算双份首屏 UI。
- CI 全绿只证明编译与断言成立，不证明听感或帧率。
