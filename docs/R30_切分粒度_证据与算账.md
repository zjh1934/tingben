# R30 · 「拆这么细有没有必要」——证据与算账

> **纯回答轮**：不动代码、不改 prompt、不发包、不调缓存分桶。只把事实、公式、真机日志摆齐，算完给结论。
> 范围锁定：**只用现有两个模型**（Qwen3-4B-abliterated Q4_K_M + Qwen3-TTS-12Hz-1.7B-VoiceDesign Q8_0 + 12Hz tokenizer）。「换模型」按用户要求不讨论。
> 证据分级：**A** 官方一手 / **B** 本地源码或公式推导 / **M** 本项目真机实测 / **C** 社区实测 / **D** 二手待核。

---

## 0. 一句话结论

**三层「细」，只有一层是真硬约束，另外两层是我们自己写的契约逼出来的，不是模型能力逼的。**

| 层 | 现状 | 判定 |
|---|---|---|
| 两个模型分两阶段加载（先全标完、释放 LLM、再开 TTS） | 强制 | **真硬约束**，内存决定，不能改 |
| 标注块 350~500 字 | 试音短篇 545 字 → 2 块 | **没有硬理由**，是历史参数；但放大它也省不了多少 |
| 朗读段 68~110 字 | 545 字 → 8 段 | **偏碎**，方向没错，可适度放大 |
| 每条标注 `text` 到句级 | 逐条 speaker/instruct | **必须保留**，这是 instruct 的附着单位 |

真正逼我们细的，不是「4B 只能看 500 字」或「TTS 只能读 110 字」，而是**我们让 4B 逐字回显原文**这个契约。

## 1. 硬参数（模型能给到哪）

### 语言模型 Qwen3-4B

| 项 | 值 | 等级 | 出处 |
|---|---|---|---|
| 原生 `max_position_embeddings` | **40960**（32768 输出 + 8192 prompt 预留） | A | HF `config.json` [citation:5][citation:9] |
| YaRN 扩到 131072 | 可行，但官方明确「平均上下文不超过 32768 **不建议启用**，可能降低短文本性能」 | A | Qwen3 官方 README [citation:5] |
| 架构 | 36 层 / 32 Q heads / **8 KV heads** / head_dim 128 / GQA | A | HF `config.json` [citation:9] |
| KV cache 每 token | `2 × 36 × 8 × 128 × 2B = 147,456 B = 144 KiB`（f16） | B | 公开公式 + 上列配置 [citation:11][citation:12] |
| n_ctx=4096 预留 KV | **576 MiB，启动即分配，与实际 prompt 长度无关** | B | 同上；「allocation is not lazy and does not grow」[citation:12] |
| n_ctx=8192 / 32768 | 1.125 GiB / 4.5 GiB | B | 同上 |

**关键**：模型原生能看 4 万 token，我们设 4096 是**内存选择**，不是模型上限。

### 音频模型 Qwen3-TTS 12Hz 1.7B（本地一手源码）

| 项 | 值 | 等级 | 出处（本地文件） |

### 平台

Android 官方：每个 App 进程堆有**硬上限**，超过 OOM；内存不足时系统「考虑终止占用最多内存的进程」[citation:7]。

同时驻留估算（B/M）：
```
4B Q4_K_M      2.50 GiB  （用户日志实测 2,497,280,544 B）
KV @4096       0.56 GiB
TTS talker     2.10 GiB  （GGUF README Q8_0 1.7B）
codec 12Hz     0.29 GiB
────────────────────────
合计           ≈ 5.45 GiB  （未含 Java heap / PCM buffer / 系统开销）
```

## 2. 我们实际切多细（本地源码 + 真机日志）

| 层 | 代码 | 实际值 |
|---|---|---|
| 标注块 | `Pipeline.kt:200-220` `cut()`：`len>=350 且遇句末标点` 或 `len>=500` 硬断 | 试音短篇 545 字 → **2 块** |
| 朗读段 | `TextSplitter.kt:20-23` `TARGET_CHARS=110`、`SOFT_CAP=260`、无字符硬切 | 545 字 → **8 段**（平均 68 字） |
| LLM 窗口 | `Prefs.kt:88` 默认 4096；`tingben_native.cpp:158-166` `n_batch=n_ctx`、`n_ubatch=512` | 4096 |
| LLM 输出预算 | `Pipeline.kt:958` `budget = minOf(2048, chunk.text.length*2+900)` | 日志 `limit=876` |
| TTS | `Prefs.kt:16` `MAX_NEW_TOKENS=2048`；`max_batch=1`；`on_chunk=null`（buffered） | 2048 |

真机日志（用户贴的 `1.0.0+32`，M）：
```
NATIVE_PREFILL_DONE | tokens=979 nCtx=4096 nBatch=4096 avail=3109 limit=876
ANN_WAIT            | 块 1/2 仍在算 · 已 535s → 605s（prefill ≈ 600 秒）
NATIVE_DECODE_STEP  | token=0 → token=96，每 8 token 约 2.6~3.3s（≈0.33~0.41 s/token）
ANN_BLOCK_END       | 块 1/2 结束 · 0 条标注 · 耗时 643428ms
DIRECT_READ         | 2 块跳过标注，切成 8 段直接朗读
TTS_INPUT           | 段 1/8 textChars=88；段 2/8 textChars=64
```

**窗口利用率**：prompt 979 / 4096 = **23.9%**；prompt + 输出预算 = 979 + 876 = 1855 / 4096 = **45.3%**。窗口还空 **2241 token**。

## 3. 逐层判定

### ① 两阶段加载：真硬约束，别动

5.45 GiB 同时驻留，撞 Android 单进程硬上限；官方明确内存不足优先杀最占内存的进程 [citation:7]。这正是「先全标完 → 释放 LLM → 再合成」和「不能边标边合、不能并行」的理由。

**但这条只要求「分两阶段」，不要求「每一阶段内部拆细」。** 两个阶段各自处理多少字，是另一回事。

### ② 标注块 500 字：没有硬理由，但放大它也不是解法

**不是上下文逼的**：模型原生 40960，我们 4096，prompt 只占 24%。
**不是内存逼的**：576 MiB KV 是**预分配**，块大小不改变它。
**是输出契约逼的**：我们要求模型把原文逐字回填进 JSON，输出 token ≈ 块字数 × 1.5~2。

按窗口算物理上限：

| 块大小 | prompt 估算 | 输出需求（回显 JSON） | 合计 / 4096 | 结论 |
|---|---|---|---|---|
| 500 字（现状） | 979 | 876（日志实测） | 1855 | ✅ |
| 1000 字 | ≈1479 | ≈1750 | ≈3229 | ✅ 仍放得下 |
| 1500 字 | ≈1979 | ≈2600 | ≈4579 | ❌ 溢出 |

所以**现有契约下块的物理上限约 1000~1200 字，500 字确实偏保守，可以翻倍**。

但算时间账（用真机单位成本，M，prefill 按线性外推属乐观估计）：

```
现状 2 块 × (600s prefill + 876 tok × 0.37s ≈ 324s decode) ≈ 1848s ≈ 30.8 分钟
合并 1 块 1000 字：
  prefill ≈ 1479 × 0.61 ≈ 902s
  decode ≈ 1750 × 0.37 ≈ 648s（KV 更长，实际只会更慢）
  合计 ≈ 1550s ≈ 25.8 分钟  →  省约 5 分钟 / 16%
```

省的主要是**系统提示词 968 字（≈700 token）每块重复 prefill**：2 块→1 块省 ≈427 秒 ≈7 分钟。

**结论**：总 token 量守恒（原文要 prefill 一遍、再 decode 回显一遍），放大块几乎打平；而且 gate 一旦失败，降级损失从 500 字变成 1000 字。**调粒度是低收益动作。**

### ③ 每条标注到句级：必须保留

`instruct` 是「这一段怎么说」的指令，粒度必须到语气单元，否则「压着怒气」「句尾下沉」无从附着。官方 VoiceDesign 的 instruct 本身就是整段一句自然语言；Alexandria 的 `style` 逐行、Antioch 的 `voice instruction` 逐行，都是这个粒度。

**要改的不是「标多细」，是「要不要让模型把原文再抄一遍」。**

### ④ 朗读段 110 字：偏碎，方向没错，可放大但别贪

**不是硬限制**：2048 token / 12.5 Hz = 163.8 秒；按真机 545 字 → 121 秒音频（`+14` 日志 5,802,284 B ÷ 48,000 B/s ≈ 120.9 s）≈ **4.5 字/秒** → 单段理论上限 ≈ **738 字**。现在 68~110 字只占上限 **9~15%**。

**但拆细有真实代价**（B，`qwen.h` 注释）：引擎内部 codec 按 24 秒切解码，任何切分留 −50 dB 残差；我们自己的每段边界还多一次 `qt_synthesize`、一次静音拼接、一次 WAV 文件。8 段 = 8 次调用 + 7 处拼接。

**反过来也有风险**：社区实测长文本语速越来越快 [citation:6]；真机 RTF≈17，一段 260 字 ≈ 58 秒音频 ≈ **16 分钟单次调用**，被杀或失败损失是现在的 4 倍，断点粒度也变粗。

**注意一个容易混的点**：`codec_chunk_sec=24s` 是**单次合成内部**的解码分块，不是我们把文本切成多段。即使一次喂 700 字，引擎内部仍按 24 秒切、仍留残差；减少的是「我们自己的」边界，不是全部边界。

**官方 batch 也救不了**：官方 Python 可以 `text=[句A, 句B]` 一次调用，但 qwentts.cpp 的 `max_batch>1` 在 GPU 上才合并 decode，CPU 是单 compute worker 串行（`qwen.h:133-141`）。我们 `max_batch=1`，指望「一次传 8 段变快」不成立。

## 4. 那到底该改什么（按收益排序）

| 优先级 | 动作 | 估算收益 | 代价/风险 |
|---|---|---|---|
| **1** | **骨架化标注**：程序切句/归属，4B 只输出「区间号 + 角色 + 指令」，不回显原文 | 输出 876 → ~100 token，decode 324s → ~37s，**单块省 ≈48%**；且输出不再随块大小增长，块可放大到 2000+ 字仍不溢出 | 改契约、gate 改成区间覆盖、缓存/日志联动，单列一轮 |
| **2** | 标注块 500 → 1000 字 | 省 15~23%（主要是省一次系统提示词 prefill） | gate 失败损失翻倍；收益远小于 1 |
| **3** | 朗读段 110 → 200~260 字 | 段数 8 → 2~3，减少拼接边界与调用开销 | 单次失败损失 4 倍、社区报告的长序列韵律漂移，需真机 A/B |
| — | n_ctx 4096 → 8192 | 不解决任何一层 | KV 576 MiB → 1.125 GiB，直接把 5.45 GiB 推到 6 GiB+，OOM 风险，**不建议** |

**一句话**：拆细不是目的，是「让 4B 逐字回显原文」这个契约的副作用。**改契约 ≫ 调粒度 ≫ 调窗口。**

## 5. 证据等级与限定（不夸大）

- **A 官方**：Qwen3-4B `config.json` 40960/36层/8KV；官方 README 的 YaRN 建议与 long-zh 评测；官方示例句子级 + `max_new_tokens=2048`；Android 内存管理文档。
- **B 源码/公式**：本地 `qwen.h` / `sampling-defaults.h` / `Pipeline.kt` / `TextSplitter.kt`；KV 144 KiB/token 推导。
- **M 真机实测**：`promptTokens=979`、prefill ≈600s、decode ≈0.37s/token、0 条标注、`TTS_INPUT textChars=88/64`、545 字→121 秒音频。
- **C 社区**：长文本语速漂移 [citation:6]，无 commit/音频样本/对照实验，只作风险提示。
- **限定**：
  1. long-zh 评测是 **CustomVoice**，我们是 **VoiceDesign**；WER 测内容一致性，非韵律自然度。
  2. KV 144 KiB/token 按 **f16 K/V** 推，实际 GGUF 若量化 K/V 会更小；576 MiB 是上界。
  3. prefill 按 token 线性外推**偏乐观**，attention 随长度超线性，实际放大块可能更慢。
  4. 全部「更省时间」是**算出来的**，没有一个在 24117RK2CC 上跑过 A/B。真机仍是零证据。
