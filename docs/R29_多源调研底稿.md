# 「听本」离线有声书链路：Qwen3-TTS 语义能力、更强模型、K80 现实可行性及升级优先级研究

## 摘要

截至 2026 年 11 月 4 日，用户当前使用的 Qwen3-TTS-12Hz-1.7B-VoiceDesign 并非完全“不会理解语义”：官方明确声称，它可同时利用显式自然语言 instruct 和输入文本语义，自适应调整语调、节奏与情绪表达；VoiceDesign 的输入是音色/人设描述，而不是单纯选取预设音色。但它没有被官方承诺为“无需指令、自动判断小说角色情绪、说话人和非语言事件”的端到端语音语言模型；“不给 instruct 也能读懂小说”没有官方实锤。Qwen3-TTS 官方模型矩阵也没有列出 `[laughs]`、`[gasp]` 等行内标签，这类能力应归入后来的 Qwen-Audio-3.0-TTS，不能移植到当前 GGUF 模型。[2][3][7]

在候选模型中，真正兼顾“更强语义控制”和“现实可本地替换”的并不多。Qwen3-TTS-1.7B-CustomVoice 可以直接用相同 qwentts.cpp 权重接口替换，前提是 JNI 也暴露 speaker 与 instruct；0.6B 两版并不因为参数量小就自动支持 VoiceDesign。Qwen-Audio-3.0-TTS 的行内标签与连续语音控制能力更强，但公开证据显示它是 API/云端服务，没有找到可本地 GGUF 或 qwentts.cpp 引擎的证据。其他端到端语音模型如 GLM-4-Voice、MiniCPM-o、VoxCPM 及条件式 IndexTTS2、CosyVoice 3，通常只能在 PC 或 K80 上预生成，换成非 Qwen3-TTS 架构基本等于新增推理引擎并可能重写 JNI。[5][12][17][18]

K80 是 Kepler GK210、双芯各约 12GB、24GB 总显存、计算能力 3.7；没有 Tensor Core、没有硬件 BF16，CUDA 11.0 已把 sm_35/sm_37 列入弃用。PyTorch 2.0.0/2.0.1 仍提供 cu117/cu118 wheel，但那只是安装入口，不能据此认定支持 K80；FlashAttention 官方适用门槛约为 Ampere 8.0。因此 Qwen3-TTS GGUF 是 K80 上唯一“直接换权重即可”的现实路径，其他方案至少需旧版 CUDA/PyTorch 源码构建，并可能遇到 cuDNN、Python、驱动、FlashAttention 或 BF16 权重兼容问题。

## 一、Qwen3-TTS 的“语义自动调节”是有条件的，不是无监督小说理解

**官方口径里，模型会同时响应显式指令和文本语义，但「文本语义自适应」不等于自动角色理解。** Qwen3-TTS 官方技术页面把能力概括为：利用文本指令和文本语义进行上下文理解，自适应控制语调、语速与情绪；官方 Python 接口 `generate_voice_design` 接收 `text` 与 `instruct`，典型 instruct 是“体现撒娇稚嫩的萝莉女声，音调偏高且起伏明显”这类自然语言描述。[2][4] 因此，模型可以做到“同一句文本在不同 instruct 下形成不同语调、节奏、情绪”，也能在给定指令范围内根据文本内容调整韵律；但“自动判断小说里谁在说话、这句话应悲伤还是愤怒”超出了已公开的能力承诺。

可以把 VoiceDesign 理解为一个条件化生成器：显式 instruct 决定目标音色/人设/表演风格，文本提供语言内容和局部语义，二者共同形成条件。它不是项目当前 LLM 层不存在时可自行补位的小说理解器。现有链路中，如果 LLM 只输出 `text/speaker/instruct` 而不判断情绪、关系、语境和不可说内容，把自然度不足归因于 1.7B 音频模型并不严谨；音频模型没有 LLM 提供的语义标签时，只能从文本字面、已有指令和训练先验推断。

**VoiceDesign 的核心产物是“设计出的音色身份”，CustomVoice 的核心产物是“既有音色的风格变化”。** 官方模型矩阵显示，1.7B-VoiceDesign 按用户描述创建声音；1.7B-CustomVoice 使用 9 个内置音色，并允许自然语言指令对目标音色施加风格控制；Base 面向零样本音色克隆。[2] 两者都支持 instruct，但优化对象不同。对有声书而言，CustomVoice 更适合“固定角色池＋逐句风格”，VoiceDesign 更适合为每个角色构造长期一致的新人设；但 VoiceDesign 每次都只用一条描述固定音色，不能据此假设它会自动记住多角色跨章节状态。

**0.6B 与 1.7B 的差别主要是控制覆盖和能力预算，而不是 0.6B 能自动理解、1.7B 不能。** 官方矩阵中，0.6B 只有 CustomVoice 和 Base，没有 VoiceDesign；1.7B 三档齐全，官方将其定位为更高性能与控制力。[2] 这不意味着 0.6B-CustomVoice 收到 instruct 时必然能取得和 1.7B-CustomVoice 相同的一致性。公开社区材料甚至声称 0.6B 系列即便传 instruct 也会被忽略，但这是社区实现侧解读，不能当作 Qwen 官方承诺，必须用具体 commit 的 `qwen-tts` 代码、Prompt Builder 和生成参数复核。

| 模式 | 0.6B | 1.7B | 官方核心输入 | 对项目最合适用途 |
|---|---:|---:|---|---|
| Base | 有 | 有 | 参考音频/文本、命名说话人 | 稳定复用同一参考音色 |
| CustomVoice | 有 | 有 | 9 音色 + 自然语言 instruct | 固定角色池＋逐句风格 |
| VoiceDesign | 无 | 有 | 自然语言音色/人设描述 | 创造新角色音色 |

**Base 也不是「无指令自动表演」模型。** 官方 Base 的定位是零样本克隆基座，1.7B-Base 的模型卡同样列出支持 10 种语言、流式与语音生成，但没有把“自行根据小说理解情绪”写成能力。其语言栏有 instruct 标记，可能指某些说话人/语言或通用条件，但不足以证明 Base 会自动输出丰富情绪。若项目追求的是自然表达，应把 Base 视为音色复现组件，而不是取代 LLM 语义层的推理器。[5]

## 二、行内非语言标签来自另一代 Qwen 模型，不能假设 Qwen3-TTS 已支持

**Qwen3-TTS 官方接口与模型矩阵没有列出 `[laughs]`、`[gasp]` 等行内标签。** 官方 Python 文档展示的是 `speaker + instruct + text` 的组合，例如 CustomVoice 用“用特别愤怒的语气说”，VoiceDesign 用完整声音描述；示例文本均为正常对白，未出现 `[gasps]`、`[laughs]` 这类插入式标签。[4] 官方模型卡的能力表也未包含行内事件控制。[2][5] 所以把 `[gasp]` 直接写进 `text`，在 Qwen3-TTS 中可能产生三种结果：模型按文字读出标签、当作表演提示但不稳定、或产生难预测的音素；这不是当前公开证据能够承诺的稳定控制通道。

**Qwen-Audio-3.0-TTS 才是官方明确支持细粒度行内控制的新一代产品。** Qwen 官方发布称其支持自然语言指令和 86 个细粒度行内标签，可控制情绪、笑声、耳语、呼吸等，并提供 Flash/Plus 不同服务层级；公开摘录还显示其发布于 2026 年，模型本身具有端到端生成能力。[7] 这恰好说明行内事件能力已经出现，却也提示它属于不同于 Qwen3-TTS-12Hz 的模型代际或服务形态。不能用 Qwen-Audio-3.0-TTS 的 86 标签能力反推 1.7B-VoiceDesign 已支持。

**判断时应严格区分 API 模型、开源权重和 GGUF 推理器。** Qwen 另有 `Qwen3-TTS-VD-Flash` 与 `Qwen3-TTS-VC-Flash`，官方明确给出通过 Qwen API 使用的代码示例；发布页同时声称它们可依据语义自动调整语调和节奏，支持自然语言控制音色、韵律、情绪、人设。[1] 这是 API 模型的官方声称，不等于本地 1.7B GGUF 使用完全相同的数据、指令模板或行内标签集。用户当前 Android 链路无 INTERNET 权限，因此即使 API 更强也不能“用上”。

| 证据层级 | Qwen3-TTS-12Hz-1.7B | Qwen-Audio-3.0-TTS / VD-Flash | 对项目的含义 |
|---|---|---|---|
| 官方明确 | text+自然语言 instruct；按语义调整语调、节奏、情绪 | 自然语言 + 86 行内标签；情绪、呼吸、笑声等 | 行内事件只有新一代 API 有强证据 |
| 代码/文档实锤 | 官方 Python 接口字段、模型矩阵、Q8_0/BF16/F16 模型 | 官方发布与 API 文档 | 可据此设计 prompt，不能移植标签 |
| 未找到证据 | Base/0.6B 自动角色理解；行内事件 | 可下载 GGUF、qwentts.cpp、Android 离线运行 | 不能写成“支持” |

## 三、官方声称、代码实锤与“社区实测”必须分开，现有证据不支持把模型当成黑箱导演

**官方声称足以证明受控条件生成，却不足以证明跨句长期戏剧理解。** 官方可证明的能力是：instruct 控制音色/风格，文本条件影响韵律与情绪，VoiceDesign 创建新声音，CustomVoice 在既有音色上做风格迁移。要证明“模型自己读懂小说”，至少需要官方文档说明其可直接接受长剧本并自动推断角色、情绪、非语言事件，或开源代码中存在剧本解析与角色状态模块。当前公开官方材料没有这些证据。

**代码实锤应当落在具体接口，而不是二手“端到端”标签。** 可核验的官方代码路径是：`Qwen3TTSModel.from_pretrained` → `generate_custom_voice(text, language, speaker, instruct)` 或 `generate_voice_design(text, language, instruct)`；模型以 BF16 加载、可选 FlashAttention-2。[4] 这说明推理器确实把 instruct 显式传入模型，而不是仅凭运行时猜测。项目若想最大化现有模型，应让 LLM 给每一块文本产生稳定、可校验的 `instruct`，而不是期待音频模型读取整章剧情。

**“社区实测”只能提出待验证假设。** 社区页面称 0.6B 传 instruct 会被自动忽略、或声称模型可“结合文本自动理解情绪”，这些说法没有同时给出 commit、prompt、音频样本与对照实验，不能成为替换决策依据。用户已测得 RTF≈17，这证明当前端侧吞吐严重不足，却不能单独证明问题在 LLM 契约、音频模型、Android NDK/GGML 后端还是块长度；应保留同一文本集、同一采样条件做消融，而不是凭观感换模型。

## 四、真正“能自己理解语义”的开源模型数量少于表面候选名单

**端到端语音语言模型与条件化 TTS 应分开评价。** 端到端语音语言模型一般把语音/文本共同置于模型上下文，能利用语言理解决定声学输出；条件化 TTS 则仍以文本 token、参考音频、风格 prompt 为显式条件。前者有更强的潜在语义能力，但不必然更可控；后者控制接口明确，却容易在未见标签或情绪上失效。

| 模型 | 是否端到端语音语言模型 | 语义/情绪/非语言事件 | 许可与尺寸 | GGUF/llama.cpp/端侧支持 | 项目可用性判断 |
|---|---|---|---|---|---|
| Qwen3-TTS 1.7B | 否，离散码本条件生成 | 显式 instruct；文本语义影响韵律 | Apache-2.0；约 1.7B talker | 官方 GGUF、qwentts.cpp；Q8_0 约 2.1GB | 现有链路直接可用 |
| Qwen-Audio-3.0-TTS | 官方声称为端到端 | 自然语言 + 86 行内标签 | 未找到可本地 GGUF | 未找到官方本地推理器 | 仅 API，不能离线 |
| Qwen3-Omni / Qwen2.5-Omni | 是，原生多模态 | 理解多模态；行内 TTS 控制证据不足 | 部分权重开放 | 无官方 llama.cpp 路径 | PC 理论可跑，Android 无实锤 |
| Step-Audio 2 | 官方声称为端到端语音模型 | 自然语言控制 | 未找到可下载 Step-Audio 2 本地权重 | 未找到 GGUF | 不能落成本地 |
| GLM-4-Voice | 是，语音理解与生成 | 可调整情绪、语调、语速、方言 | 官方仓库与权重开放；具体许可证以仓库为准 | 官方是 PyTorch 服务；无 GGUF/Android | PC 现实可跑 |
| MiniCPM-o | 是，端到端多模态 | 多模态理解及语音生成 | 开放部分模型 | 无官方 llama.cpp | PC 可部署，端侧代价高 |
| IndexTTS2 | 否，零样本 AR-TTS | 情绪与音色解耦；软文本指令 | Apache-2.0；权重开放 | 无官方 GGUF | PC 现实可跑 |
| CosyVoice 3 | 否，条件式生成 | 自然语言指令、上下文克隆 | Apache-2.0；权重开放 | 无官方 GGUF/llama.cpp | PC 现实可跑 |
| VoxCPM-0.5B | 是，上下文感知生成 | 官方强调上下文，无行内事件实锤 | Apache-2.0；约 0.5B | 社区 VoxCPM.cpp，官方仍在质量验证 | PC 现实可跑但需验证 |
| Seed-TTS | 否，AR LM + 扩散/声码 | 官方报告称可控制情绪、生成笑声 | 仅技术报告，未找到官方权重 | 无 | 不能用 |
| Fish-Speech / OpenAudio | 否 | 自然语言与停顿/笑声/叹息类控制 | 代码与权重开放 | 无官方 GGUF | PC 现实可跑 |
| Hume Octave | 否，服务模型 | 连续情绪空间 | 闭源 API | 无 | 不能离线 |
| ElevenLabs v3 | 否，服务模型 | 行内语音标签 | 闭源 API | 无 | 不能离线 |

**“更强”不等于“对本书更自然”。** GLM-4-Voice 是端到端 9B 语音聊天模型，可调整情绪、语调、语速和方言，适合验证语义理解型生成；但它面向实时对话，不是现成的有声书双 GGUF 流水线。[17] IndexTTS2 强调情绪与音色解耦，适合比较“显式情绪 prompt”能否提升一致性，却没有证据表明能自己阅读整部小说。[18] VoxCPM 的 0.5B 尺寸与上下文感知定位很适合 K80 实验，但社区 C++ 运行时的质量对齐仍在进行，不能仅凭“有 GGUF”认定为生产可用。[24]

**Seed-TTS 与闭源 API 是两张不同的“不能用”清单。** Seed-TTS 技术报告展示了强零样本克隆和情绪控制，但截至研究截止没有找到官方可下载权重，只能排除。[21] Hume Octave 和 ElevenLabs v3 的行内/连续情感控制可能很适合小说，却都要求联网，会破坏当前离线硬约束。Seed-TTS 是“研究可用但部署不可用”，后者是“能力可用但架构不可用”，二者不能混为一项。

## 五、K80 能装得下 Qwen3-TTS，但现代工具链已经把它推到旧软件时代

**K80 的架构事实是 Kepler、sm_37、双 GPU、每芯约 12GB，全板约 24GB，无 Tensor Core 和无硬件 BF16。** NVIDIA 官方设备说明和发行资料确认 Tesla K80 为双芯加速器，12GB/芯、2496 CUDA 核心/GPU；NVIDIA GPU 目录把 K80 列为计算能力 3.7 的 Kepler 产品。[10][11][19] 这意味着 1.7B Q8_0 talker 约 2.1GB、tokenizer 约 291MB 的官方量化尺寸在容量上完全放得下，但这只是显存容量结论，不是推理性能或软件兼容结论。[15]

**CUDA 11.0 已弃用 sm_35/sm_37，K80 已进入“能编译不代表有官方支持”的阶段。** NVIDIA CUDA 11.0 发行说明明确写道：Kepler sm_30/sm_32 支持被移除，sm_35 与 sm_37 被弃用。[20] 后续 CUDA Toolkit 的官方页面搜索结果进一步表明，Kepler 支持已在较新工具链中消失。项目若使用 2026 年的现代框架，应默认 K80 没有官方支持，而不是寻找某个声称“仍然可用”的博客作为依据。

**PyTorch wheel 的存在只说明安装器有对应 CUDA 构建，不能证明 K80 被该 wheel 支持。** PyTorch 官方 Previous Versions 页面明确列出 PyTorch 2.0.0/2.0.1 的 CUDA 11.7 与 11.8 wheel。[13] CUDA 11.7/11.8 对旧卡的支持仍比 CUDA 12/13 现实，但用户仍须在真实驱动、glibc、Python、PyTorch、cuDNN 组合中实测 `torch.cuda.is_available()` 与张量计算。PyTorch 官方版本发布说明本身没有逐字承诺“cu118 wheel 支持 sm_37”，因此这是版本选择推断，不是官方支持声明。

**FlashAttention 基本不适用于 K80。** FlashAttention 的官方要求与社区版本矩阵都把适用硬件推向 Ampere 8.0 及以上；K80 的 Kepler 3.7 没有相应硬件加速前提。[12][14] Qwen3-TTS 官方示例可指定 FlashAttention-2，但 K80 不应开启；更现实的是普通 attention 或框架回退，并预期明显更慢。FA 不可用不会自动使模型不可运行，却可能改变延迟和显存，不能照搬 Ampere 配置。

| 技术条件 | K80 结论 | 对候选模型的含义 |
|---|---|---|
| 24GB 总显存 | 能装 Qwen3-TTS 1.7B Q8_0 + tokenizer | 不是端侧 Android 的替代品 |
| Compute 3.7 | 无 Tensor Core，无硬件 BF16 | 需要 FP32/FP16 路径或软件 BF16 模拟 |
| CUDA 工具链 | 11.0 已弃用 sm_37；新版更差 | 应选 CUDA 11.7/11.8 旧环境 |
| PyTorch | 2.0.x cu117/cu118 有 wheel | 需源码构建或在旧发行版验证 |
| FlashAttention | 不适合 Kepler | 关闭 FA2，不能用“不支持”当“不能跑” |
| llama.cpp GGUF | 有 sm_37 社区构建实践 | 只适用于 llama.cpp 兼容模型，不适用全部 TTS |

**Qwen3-TTS GGUF 在 K80 上是“现实可跑”，其他模型主要是“理论可跑”。** 现实可跑意味着官方权重格式、官方 C++ 运行时、显存需求和 CUDA 后端均已存在；理论可跑只意味着模型权重开放、PyTorch 能表达算子、显存可能装下，但仍需旧 CUDA、旧 PyTorch、缺失算子补丁、量化转换与完整回归。VoxCPM 的社区 C++ 运行时尤其体现这一点：有 GGUF 和端到端推理代码，不等于 AudioVAE V2 输出和模型质量已经与官方完全对齐。[24]

## 六、三类替换路径的边界清晰：换权、预生成、联网 API 不能混为一谈

**第一类只有 Qwen3-TTS 同家族 GGUF 能直接换进 qwentts.cpp。** 官方 Qwen3-TTS GGUF 仓库说明每次需加载 `qwen-talker` 与 `qwen-tokenizer-12hz` 两个 GGUF；Q8_0 1.7B talker 约 2.1GB，tokenizer 约 291MB，运行时支持 CPU、CUDA、Metal 和 Vulkan。[15] 同一仓库明确提供 base、clone、customvoice、voice design 四种示例。由此可见：

1. 从 Base 换成 1.7B-CustomVoice，只需换 talker GGUF 并确认 JNI 传入 speaker/instruct；
2. 从 Base/CustomVoice 换成 1.7B-VoiceDesign，同样无需替换 tokenizer 或 codec，但仍要提供 VoiceDesign 的 prompt 接口；
3. 换成 0.6B-CustomVoice 也保留 tokenizer 不变，却会失去 VoiceDesign 且控制能力未知；
4. 换成任意非 Qwen3-TTS 的 GGUF 并不能“直接运行”，除非它恰好复用相同 talker/codec 格式。

**第二类是在 PC/K80 上预生成音频文件，再导入手机，但这会破坏离线架构边界。** K80 上可以离线，Android 端也可继续无网络；可是生产链路变成“下载书→在 PC 生成→传回设备”，对只读手机和一次性生成场景尚可，对动态试听、局部重合成、中途改人设、存储有限和自动更新并不友好。文件体积也是现实成本：24kHz 单声道 PCM/WAV 每分钟约 2.88MB，长篇有声书需显著存储；若预生成所有候选风格，空间还会成倍增加。

第二类真正适合的是受控对照实验，而不是主链路。可用 K80/PC 分别渲染同一句对白：无 instruct、强 instruct、IndexTTS2 情绪 prompt、GLM-oice/VoxCPM 输出、Qwen-Audio-3.0-TTS API 输出。用固定脚本盲听比较音色一致性、断句、情绪强度与副语言，再决定是否值得接受“PC 预生成”的架构代价。

**第三类是联网或闭源 API，应明确排除。** Hume Octave、ElevenLabs v3 和 Qwen-Audio-3.0-TTS API 都需要网络。即使它们支持连续情绪或行内标签，也不能进入无 INTERNET 权限的 Android App。Qwen3-TTS-VD-Flash 的 API 文档还显示其通过 Qwen API 访问，并自动调整语义语调；这属于更强的官方声称，但不符合本项目硬约束。[1]

| 替换路径 | 典型对象 | 推理位置 | 能否保持 Android 离线 | 工程代价 |
|---|---|---|---|---|
| 同家族换 GGUF | 1.7B-CustomVoice、0.6B 模式、其他量化 | Android 现有 qwentts.cpp | 能 | 低至中，取决于 JNI 接口 |
| PC/K80 预生成 | GLM-4-Voice、MiniCPM-o、VoxCPM、IndexTTS2、CosyVoice 3 | 外部设备 | 链路实质非纯端侧 | 高，涉及存储、传输、版本、重合成 |
| 闭源/联网 API | Octave、ElevenLabs v3、Qwen-Audio 3.0 API | 云端 | 不能 | 低部署、高合规与持续成本 |

## 七、换成非 Qwen3-TTS 架构基本等于重写 JNI 和新增推理引擎

**qwentts.cpp 不是通用 GGUF 播放器，而是 Qwen3-TTS 专属推理图。** 源码结构公开显示，它同时实现 talker 语言模型、MTP 码预测头、SEANet/ConvNeXt/DAC codec、ECAPA-TDNN 说话人编码器、Qwen2 BPE、prompt builder、采样、KV cache 与 GGUF 张量加载。[16] GGUF 只规定张量存储格式，不规定模型计算图。把 GLM-4-Voice、CosyVoice、IndexTTS2、VoxCPM 的 GGUF 放进同一文件，也无法让 qwentts.cpp 知道其层结构、条件编码和音频解码方式。

**“能加载 GGUF”和“能推理 TTS”之间相差一个完整引擎。** 替换代价可按四层评估：

| 层 | Qwen3-TTS 现状 | 换非家族模型的增量 |
|---|---|---|
| 文件层 | talker + 12Hz tokenizer | 可能只需一个模型、多个文件或 codec/flow decoder |
| 图层 | talker/MTP/codec 专属实现 | 必须移植新模型前向或绑定其推理库 |
| 条件层 | text、language、speaker、reference、instruct | 可能变为参考音频、style token、reference text、事件 token |
| 接口层 | qwentts.cpp 的 C ABI/JNI | 若只换同家族可复用；否则需新 ABI、缓冲区与生命周期 |

**JNI 是否需要重写取决于替换边界，而不是模型名称。** 若仍用 qwentts.cpp，只从 Base 换到 1.7B-CustomVoice 或 VoiceDesign，JNI 通常只需扩展 C ABI 调用、参数与错误码，不必然重写。若采用 GLM-4-Voice/MiniCPM-o/VoxCPM，则要在 Android 上移植其 C++/PyTorch 引擎，或保留服务端。若采用 IndexTTS2/CosyVoice，则通常需 PyTorch/ONNX 运行时及模型专属预处理。若 VoxCPM 的社区 C++ 运行时成熟，理论上可最小化 JNI，但仍要重新映射说话人、条件和音频输出。

**最经济的短期实验不是重写 JNI，而是把现有模型调用做成可插拔接口。** 定义 `synthesize(text, language, voice_ref, instruction, event_tags, override_audio)` 的稳定 JNI 接口，让 Base/CustomVoice/VoiceDesign 都实现同一抽象。这样后续增加预生成导入或实验性引擎时，音频输出层、缓存层和任务调度层不需全部重写。

## 八、同类有声书项目一致证明：自然度的关键在 LLM 输出契约，而非只选一个声音

**Alexandria 明确把 LLM 变成“剧本导演”。** 其官方 README 描述的工作流是 LLM 生成含 speakers、text、style 和 non-verbals 的 JSON，随后由 Qwen3-TTS 执行；默认 LLM prompts 用于脚本生成，另有 review prompts 做二次审校，并由 persona 生成与 VoiceDesign 分配角色声音。项目输出为 MP3、带章节 M4B 或 Audacity 多轨工程。[8] 这证明“标注层理解语义、TTS 层执行声学”是成熟范式，而不是过度设计。

Alexandria 的脚本 JSON 将 `style` 与 `[gasps]` 等非语言 cue 分开：前者是连续风格，后者是插入式事件。例如说话者可配“tense, suspenseful”，对白可写 `[gasps] Who's there?`，风格为“frightened, whispered”。[8] 这个分层很重要：把 `[gasps]` 直接当文本合成，只是把事件表达交给音频模型；更可靠的是单独调度非语言音段或高质量音效，再与主对白交叉淡化，避免模型用文字念出标签。

**Antioch 证明了 qwentts.cpp 在 Rust 工具链中的直接可集成性。** Antioch 的流水线为 Markdown → llama.cpp LLM 标注 → 每行 JSON 含 speaker、text、voice instruction → qwentts.cpp 生成 WAV → Rust 合并 → 可选 FFmpeg 打包 M4B。它明确使用 Qwen3-TTS GGUF 和 voice cloning，并把 LLM 的 voice instruction 直接传到 TTS。[9] 这与“听本”现有架构最接近，说明升级重点可以放在 JSON 契约，而不是立即换掉声学引擎。

**Alexandria 与 Antioch 的差别在于标签颗粒度，而不是有没有 LLM。** Alexandria 显式区分 style 和非语言 cue；Antioch 将 voice instruction 作为逐行字段。项目若只保留 `instruct="angry"`，信息量仍太低；至少应表达“对谁、因何、强度多大、持续多久、何时恢复旁白语气”。ReaderVoice-Mobile 的资料也强调角色不是单纯映射到固定发音人，而是角色语义状态机；但本次未拿到可逐字引用的官方仓库原文，故只能作为设计方向，不能据此声称其已实现某种具体标签。[10]

| 项目 | LLM 标注字段 | 非语言事件 | 语义审核 | TTS 执行 |
|---|---|---|---|---|
| Alexandria | speaker、text、style、non-verbal | `[gasps]` 等 cue 入脚本 | 二次 review prompt | Qwen3-TTS，9 音色/克隆/VoiceDesign |
| Antioch | speaker、text、voice instruction | 本次未找到明确行内事件实现 | 未强调二次审校 | qwentts.cpp + Qwen3-TTS GGUF |
| ReaderVoice-Mobile | 角色语义状态机（二手资料） | 设计目标存在，官方实锤不足 | 未核实 | 多技术栈，未核实 |

## 九、把 LLM 标签从「情绪名词」升级为「可执行的表演指令」能立刻放大现有 1.7B

**当前契约最大的损失，不是缺一个模型，而是把三维表演压成一维文本。** 现有 `text/speaker/instruct` 中的 instruct 若只是“悲伤”“愤怒”，音频模型必须自己决定强度、节奏、停顿、呼吸、重音和何时退出情绪。有声书相邻块还可能发生标签突变，例如从旁白突然进入角色哭腔，又切回平静叙述。若不把边界和持续时间写清，模型只能从文本末尾猜测。

建议将契约升级为：

```json
{
  "id": "c0001",
  "role": "ELENA",
  "voice_id": "elena_v2",
  "text": "你回来了。",
  "layer": "dialogue",
  "instruct": "30岁女性，压低声音，强忍哽咽，语速慢，结尾轻微颤抖",
  "emotion": {
    "name": "sad_suppressed",
    "intensity": 0.72,
    "onset": "start",
    "decay": "hold"
  },
  "prosody": {
    "rate": 0.85,
    "volume": -3,
    "pitch_delta_st": -1.5
  },
  "non_verbal": {
    "pre": [],
    "inline": ["[swallows]"],
    "post": ["[soft_sob]"]
  },
  "continuity": {
    "chapter": 3,
    "scene": 12,
    "beat": 4,
    "voice_lock": true
  }
}
```

**数值强度不应成为音频模型的新咒语，而应先成为实验变量。** Qwen3-TTS 官方接口没有承诺 `intensity=0.72` 会被直接解析；因此第一阶段只把强度用于 JNI/调度层：低强度事件减少停顿与音色偏移，高强度事件插入独立非语言片段，或分段选择不同 instruct。第二阶段若发现 1.7B 对“轻微担忧”与“濒临崩溃”没有区分，再考虑把强度映射到 prompt 模板。这样模型替换时，契约仍可保留，只是换执行器。

**非语言事件应分三层处理，而不是全部塞进文本。** 第一层是文本内韵律标记，例如逗号后延长的停顿；第二层是可由 TTS 用 prompt 模拟的叹息、哽咽、耳语；第三层是高价值、必须可靠的笑声、抽泣、咳嗽、喘气，由预录或独立生成片段在音频图内插入。Qwen3-TTS 没有官方行内标签承诺，所以 `[gasps]` 等不宜直接作为稳定指令。此分层既兼容当前模型，也为 Qwen-Audio-3.0-TTS 等未来模型保留转换通道。

**音色身份应由 stable voice card 管理，而不是在每块 JSON 中重写人设。** 建议建立 `voice_id → description/reference/clone-meta` 的只读目录。LLM 输出稳定 ID 与角色状态，音频层缓存同一 voice card 的 embedding 或 VoiceDesign 结果；跨章节保持角色一致，局部块只允许 prosody/event 变化。这样可避免 LLM 每次把“少女音”描述成不同音色，也能减少重复 VoiceDesign 推理。

## 十、优先级应是「契约先行、模型 A/B 验证、最后才换引擎」

**P0：保留 1.7B-VoiceDesign，补上结构化语义契约和回归集。** 现有模型官方支持 text+instruct 与文本语义自适应，说明升级 LLM 标签可立即获得收益。[2][4] 成本主要是 LLM prompt、JSON schema、JNI 字段与离线渲染任务重构；风险是 LLM 输出不合法、过度表演、标签跳变。可在不改声学引擎的前提下做 A/B：同文本下比较“无 instruct”“单层情绪”“完整 prosody+event”三组。若差异明显，升级契约的收益已高于换模型。

**P1：把 K80 用于受控离线实验，而不是立即当生产部署。** K80 可容纳 Qwen3-TTS Q8_0，CUDA 11.7/11.8 与 PyTorch 2.0.x 是最现实的旧软件组合；但 sm_37 已弃用、无 FA2、无 BF16 硬件支持，必须实测显存、计算正确性和长时间稳定性。[13][20] 用它渲染盲听样本，比较 Q4_K_M、Q8_0、F16，以及 0.6B/1.7B 模式，才能回答“现有端侧 RTF 主要是算力问题还是模型问题”。

**P2：在 PC 上做候选模型 A/B，但不承诺移植到 Android。** GLM-4-Voice、IndexTTS2、CosyVoice 3、VoxCPM、Fish-Speech 都可作为对照。每个候选至少使用同一中文小说片段、同一角色设定、同一事件标签映射，记录音色一致性、清晰度、情绪强度、非语言事件成功率、显存、合成时延和主观偏好。VoxCPM 社区 C++ 运行时虽有吸引力，但必须验证与官方 PyTorch 输出的数值/听感对齐；未经验证只能归为实验。[24]

**P3：只有当契约收益已穷尽，才把非 Qwen3-TTS 引擎移植到 Android。** 这要求新增模型图、条件编码器、codec、预处理、采样、权重管理、ABI/JNI、缓存与崩溃恢复。若采用 PyTorch/ONNX 运行时，还会显著增加包体积、冷启动、内存和兼容面。更现实的是双模式：在线/侧载创作环境使用 PC 引擎，手机仍保留 Qwen3-TTS GGUF；或者等待 VoxCPM.cpp 等社区 C++ 引擎稳定，再评估轻量 JNI 绑定。

**P4：闭源 API 只用于离线前的研究参考，不作为生产组件。** Octave、ElevenLabs v3 与 Qwen-Audio 3.0 API 可帮助建立“自然度上限”和“标签设计参照”，但不能成为无 INTERNET 应用的一部分。它们的联网、计费、内容审核、音频数据出域与版本漂移都构成硬风险。

## 十一、结论：先让 LLM 成为可靠的“剧本导演”，再决定是否给导演换演员

**对问题 1 的直接回答是：Qwen3-TTS 1.7B 会结合 instruct 和文本语义调整表达，但没有官方证据证明它能在完全没有 instruct 时自动识别小说角色、情绪和非语言事件。** 它的能力边界是“执行显式自然语言控制”与“在文本条件内自适应”，不是“自动解析整部作品”。VoiceDesign 更适合创造音色，CustomVoice 更适合在固定音色上施加表演；0.6B 没有 VoiceDesign。Qwen3-TTS 官方接口没有 `[laughs]`、`[gasp]` 等行内标签，行内事件能力属于 Qwen-Audio-3.0-TTS 这一代产品。

**对问题 2 的回答是：更强且能自己理解语义的开源模型存在，但没有一个能在不重写引擎的情况下直接进入当前 Android 链路。** GLM-4-Voice、MiniCPM-o、VoxCPM 属于端到端语音模型；IndexTTS2、CosyVoice 3、Fish-Speech 更像条件式生成器。Qwen-Audio-3.0-TTS 拥有最强公开标签能力，但目前更像 API 服务。Seed-TTS 只有技术报告，Hume Octave 与 ElevenLabs v3 是闭源 API，均不能用。

**对问题 3 的回答是：K80 现实可跑 Qwen3-TTS GGUF，其他模型大多停留在理论或实验层面。** K80 的 24GB 总显存足以装 1.7B Q8_0，但 sm_37 已弃用、无 Tensor Core/BF16、无 FlashAttention，CUDA 与 PyTorch 必须退回到仍兼容的旧组合。BF16 权重需要 FP32/FP16 转换，FlashAttention-2 应关闭。任何“K80 能跑”都应附带软件版本、显存用量和正确性日志，不能只看容量。

**对问题 4 的回答是：只有同家族 Qwen3-TTS GGUF 属于第一类；大多数候选属于第二类；闭源 API 属于第三类。** 换成非 Qwen3-TTS 架构基本等于新增推理引擎；若模型图、条件编码、codec、采样和 ABI 都不同，则 JNI 也需要实质重写。qwentts.cpp 的 GGUF 兼容只适用于 Qwen3-TTS，不意味着所有 GGUF 都能被它加载。

**对问题 5 的回答是：同类项目普遍把 LLM 作为语义层，TTS 作为执行层。** Alexandria 使用 speaker/text/style/non-verbal 的完整脚本，并有二次审校；Antioch 将 speaker/text/voice instruction 直接送入 qwentts.cpp。可借鉴的做法是增加情绪强度、事件时间位置、连续/离散风格分层、稳定 voice card，以及独立调度高价值非语言音频。

**对问题 6 的回答是：若目标是“更自然、更有语义”，优先级应是升级语言模型与标注契约，而不是先换音频模型。** 成本为 prompt/JSON/JNI 改造与回归测试；风险可控，收益可测量。换音频模型需要移植模型图、条件编码、codec 和 JNI，短期成本显著更高，且可能因许可、量化、算子或端侧性能失败。只有在现有契约达到上限，并已在 PC/K80 上完成候选 A/B 后，才应把非 Qwen3-TTS 引擎纳入主线。
