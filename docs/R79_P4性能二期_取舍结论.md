# R79 · P4 性能二期开工前取舍结论

> `ROADMAP.md` P4 条目要求「开工前先出取舍结论，不边改边试」。本文件先于任何代码改动写成。
> 只写结论与依据，不写「改完多流畅」——帧率结论不取自预览图，也不取自静态自检。

## 0. 一句话

`Column → LazyColumn` **不能全量套**：调音台的锚点用「像素 Y」比对，换列表容器会直接让标签高亮全错；
能换的只有「无锚点、行数随数据增长」的音频页。这一轮真正吃到的卡顿，主要不是列表控件太多，
而是**两处无条件定时器 + 组合期反复读磁盘**。

## 1. LazyColumn 会不会破坏 R50 锚点坐标语义 —— 会

实读 `MainActivity.kt:2118-2161` 与 `2329`：

- `val scroll = rememberScrollState()`，调音台正文是 `Column(Modifier.weight(1f).verticalScroll(scroll))`
- `anchors: MutableMap<String, Int>` 由各折叠区 `onGloballyPositioned { positionInParent().y }` 收集，
  存的是**相对整段 Column 内容的绝对像素 Y**
- `snapshotFlow { scroll.value }` 拿的是**滚动过的像素数**，`jumpTo()` 直接 `scroll.animateScrollTo(anchors[k])`

换成 `LazyColumn` 后：① item 复用，`onGloballyPositioned` 拿到的 Y 变成视口相关坐标且随复用变化；
② `LazyListState` 没有与 `scroll.value` 等价的全局像素量；③ `animateScrollTo` 的参数语义变成 item 索引。
三处同时失效，chip 高亮与点击跳转都会错。

**结论：调音台保持 `Column + verticalScroll`，一行不动。** 这是收益/风险比最差的一处，不碰。

## 2. 哪些页换、哪些不换

| 页面 | 现状 | 结论 | 依据 |
|---|---|---|---|
| 调音台 `MixerScreen` | Column + verticalScroll(scroll) | **不换** | R50 锚点像素语义，见上 |
| 目录/看书/悬浮条抽屉 `ChapterHub.kt` | 已是 LazyColumn（4 处） | **不动** | R61 已落地 |
| 音频页 `AudioScreen` | Column + `items.forEachIndexed` | **换** | 唯一「N 行随数据增长 + 无锚点」的页；R50 锚点不在这里 |
| 书架 `LibraryScreen` | Column + 书卡 forEach | 不换 | 书通常个位数；且有空态折叠/删除弹层，改了收益近零 |
| 设置 / 模型 / 制作准备 / 进度 / 任务中心 | Column + verticalScroll | 不换 | 控件数固定的表单页；折叠区高度依赖全局坐标，换列表只会引入重组抖动 |

**不宣称「9 页全量 Column」仍是现状**——`ChapterHub.kt` 早已是 LazyColumn，R51 那句对当前源码已过时。

## 3. 两处无条件循环（R51 遗留，实查确认）

1. `ChapterHub.kt:421` `MiniPlayBar`：
   `LaunchedEffect(st.isPlaying) { while (isActive) { PlayQueue.tick(); delay(1000L) } }`
   —— **没有按 `isPlaying` 门控**，且悬浮条在 `App()` 末尾**跨页常驻**。只要有过播放记录，
   暂停时也每秒写一次全局 `PlayQueue.state`，所有订阅页跟着重组。
   同时 `AudioScreen:1149` 另有 `LaunchedEffect(pq.isPlaying) { while(true) delay(500); PlayQueue.tick() }`，
   播放时**两处同时 tick** 同一个单例。
2. `MainActivity.kt:1020` `TaskCenterScreen`：
   `LaunchedEffect(Unit) { while (true) { delay(2000); loadTick++ } }` —— 不看有没有任务、也不看是否在制作，
   进这页就常驻；每 2 秒触发 `TaskResume.load / realProgress / BookStore.list` 三次磁盘读。

**做法**：悬浮条按 `isPlaying` 门控并作为**唯一 tick 源**（跨页常驻，其它页不在组合中时也能推进进度），
删掉音频页的重复 tick；任务中心定时器门控到「制作中」，静止页零定时器。

## 4. 组合期磁盘 IO

- `AudioScreen:1235` 每行 `AudioLibrary.durationMs(item.file)` → `f.length()`，N 行 = N 次 stat；
  播放时每 500ms 整页重组就重做 N 次。`AudioItem` 已从 index 带 `bytes` 字段，
  **直接用 bytes 算时长**，行内零文件访问。
- `ProgressScreen:832-850` `seenTask / segs / rest / verdict` 全都 `remember(tick, …)`，
  制作中每秒一次：`TaskResume.load`（读任务 JSON）、`Workbench.segments`（读 segmap + 最多 60 次
  `f.exists()/length()`）、`remainingCount`、`verdict`、`TaskResume.realProgress`（读整本书 + 切章 + 列目录）。
  `EventLog.lastEngine()` 是纯内存，心跳本身不读盘。
  **做法**：心跳仍跟 tick（纯内存），四项磁盘读改跟「完成的段数 `st.done`」—— 一段几十秒到几分钟，
  从「每秒一整轮」降到「每段一整轮」，语义不丢。

## 5. 明确不做

- **release-like 构建**：会动签名，`ROADMAP.md` 标「需用户点头」，本轮不碰，debug 构建不动。
- **全量 `produceState` 迁移**：`remember(refresh) { BookStore.list(c) }` 这类只在 key 变化时读一次，
  不是每帧读；全量迁移会牵动 9 页且收益有限，单列 P4b。
- **不宣称卡顿归零**：交付的是代码与断言，帧率结论不取自预览图，真机仍是零证据，按 R66 新纪律不向用户索取装机验证。
