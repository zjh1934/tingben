## 一、三个问题，各一句话

1. **现在这个 1.7B VoiceDesign 有没有「按语义调节」？**
   **有，但是有条件的。** 官方明确写它会「结合指令与文本语义，自适应调整语气、节奏、情绪表达」（A）。它**不会**自己读小说判角色、判谁在哭、自动插叹气笑声（E，官方无此承诺）。

2. **有没有更强、能自己理解语义、K80 能跑的？**
   **有，但没有一个能直接塞进我们 App。** 唯一「直接可用」的更强，是同一家族换个量化档或换个模式——**Qwen3-TTS 家族最大的就是 1.7B，没有更大的同款**。

3. **咱能用上什么？**
   最值钱的不是换音频模型，是**把 K80 用在语言侧标注和盲听对照实验上**。这轮最贴项目的一句结论：我们这台机器上，音频模型的语义能力再强也没被喂过料。

## 二、我们这个模型到底吃什么

**输入契约（B）**：`text + instruct (+ language)`；voice_design 模式下 `speaker` 传 `null`。它不是「读完整本小说自己演」，是「给一段字、给一条导演指令，把这段演出来」。

**架构（A，官方模型卡）**：离散多码本 LM + 自研 12Hz Tokenizer。模型卡里的 *high-dimensional semantic modeling* 说的是**语音信号的高维语义表征**，不是理解小说剧情——这个词最容易误读，别拿它当「模型懂故事」的证据。

**官方原话（A，qwen.ai 官方博客 / HF 模型卡）**：

> "The models exhibit strong contextual understanding, allowing them to adapt tone, rhythm, and emotional expression **based on instructions and text semantics**."
> "By deeply integrating text semantic understanding, the model adaptively adjusts tone, rhythm, and emotional expression."

拆开看是两个条件：**有 instruct**、**有这段文本**。缺了上游语义标签，它只能按字面 + 训练先验读。

**贴到我们真机上**：上一轮日志里最刺眼的一行是

```
ANN_BLOCK_END | 块 1/2 结束 · 0 条标注 · 通过 · 耗时 643428ms
```

标 0 条 → 降级直读 → `TTS_INPUT` 的 instruct 全变成「平稳、清晰地叙述，句间自然停顿」。**所以不是音频模型不会演，是根本没人给它戏。** 你之前说「不标注也不错」，其实是「降级平读 vs 直接朗读」的 A/A 对照，模型的条件控制能力从头到尾没被测试过。

**行内标签**：`[gasp]` `[laughs]` `[sigh]` `[whisper]` 等 86 个细粒度标签属于 **Qwen-Audio-3.0-TTS**（阿里云百炼 `qwen-audio-3.0-tts-flash/plus`，48kHz，1 元/万字符）。本轮实锤它是**闭源 API、不发布权重、不能本地部署**（A/B）。我们的 GGUF 不解析行内标签，写进正文会被当字念。以前我泛泛说过「下一代模型能力」，现在订正为：**不能当本地升级路径**。

**家族天花板（A）**：官方只有 **0.6B / 1.7B** 两个尺寸，1.7B 定位 "peak performance and powerful control capabilities"；GGUF 仓库同样只有 0.6B/1.7B × `base / customvoice / voicedesign`，且 **voicedesign 只有 1.7B 有**。所以「换个更大的同款」这条路，物理上不存在。

## 三、「更强」的候选，分三类

### ① 能直接换进 qwentts.cpp（不用重写 JNI）

只有 **Qwen3-TTS 同家族 GGUF**，两个 GGUF 一起加载，tokenizer 跨所有 talker 共享（B，GGUF README）：

| 换法 | 文件 | 尺寸 | 能带来什么 |
|---|---|---|---|
| 换模式 → CustomVoice | `qwen-talker-1.7b-customvoice-Q8_0.gguf` | ~2.1GB | 9 个固定音色 + instruct 风格控制，**最可能治「每小段音色不一样」** |
| 换模式 → Base | `qwen-talker-1.7b-base-Q8_0.gguf` | ~2.1GB | 3 秒参考音频克隆，需 JNI 暴露 ref 接口 |
| 换量化 → BF16 | 1.7B talker BF16 | 3.9GB + 359MB | 精度高于 Q8_0 |
| 换量化 → F32 | 1.7B talker F32 | 7.7GB + 647MB | 参考级，手机上不现实，**K80 单芯 12GB 装得下（≈8.35GB）** |

代价：2GB 级重下 + 真机复验；换 CustomVoice 要 JNI 传 `speaker`（我们已有 `ttsSpeakers()` 运行时列音色的代码，之前查过）。**这不算「更强模型」，是同一模型的更高精度 / 更稳控制。**

### ② PC / K80 上能跑，但要新引擎（不能进 App）

| 模型 | 形态 | 语义 / 情绪能力 | 显存（公开口径） | 为什么不能直接用 |
|---|---|---|---|---|
| VoxCPM2 | 2B，Apache-2.0，48kHz，Voice Design | 上下文感知、文本造声 | ~8GB | 社区 GGUF 已能端到端推理，但**质量与数值对齐仍在验证**（C/D） |
| CosyVoice 3 | 0.5B/1.5B，Apache-2.0 | 指令控制情绪、副语言标签、方言 | FP16 6–8GB | PyTorch/ONNX，无官方 GGUF |
| IndexTTS2 | 条件式 AR-TTS | **情绪与音色解耦 / 8 维情感向量** | ~6–7GB 权重，实践 12GB 卡 | 三段模型 + 独立情感模型，无 GGUF |
| GLM-4-Voice | 9B 端到端语音模型 | 可调情绪/语调/语速/方言 | PyTorch 服务 | 面向实时对话，非有声书流水线 |
| MiniCPM-o 4.5 | ~9B 端到端全模态 | 多模态理解 + 语音生成 | — | 二手资料称支持 llama.cpp/Ollama CPU 推理与多量化（**D，待核**），且是对话模型不是 TTS 权重 |
| Step-Audio 2 mini | ~8B 端到端语音 | 能理解副语言（情绪/语调/笑声） | — | 音频→音频对话模型，非文本→有声书 |
| Qwen3-Omni-30B-A3B | MoE 30B / 激活 3B，Apache-2.0 | 原生多模态 | — | 无官方 llama.cpp TTS 路径 |

**硬门槛（B）**：`qwentts.cpp` 不是通用 GGUF 播放器。它把 talker 语言模型、MTP 码预测头、SEANet/ConvNeXt/DAC codec、说话人编码器、Qwen2 BPE、prompt builder 写死在计算图里。GGUF 只规定张量存储格式，不规定计算图。换上面任何一个 = **新推理引擎 + 新 ABI + 新 JNI + 新缓存/采样/音频解码**，等于把「从零重做」再走一遍。

### ③ 明确用不上

Qwen-Audio-3.0-TTS（闭源 API）、Qwen3-TTS-VD/VC-Flash（API）、Hume Octave、ElevenLabs v3、Seed-TTS（只有技术报告、未找到官方权重）。App 无 `INTERNET` 权限，全部出局。

## 四、K80 到底能不能跑

**硬件（B/C）**：Kepler GK210，**sm_37**，一张卡是**两颗独立 GPU、各 12GB**（不是单卡 24GB；跨芯要 tensor-split，无 NVLink，走 PCIe）、无 Tensor Core、**无硬件 FP16/BF16**、每芯 240GB/s、300W。

**软件（B）**：
- CUDA 11.0 起**弃用** sm_35/sm_37，CUDA 12+ 直接不支持 Kepler；
- PyTorch 2.0 起放弃 Kepler，只剩 cu117/cu118 旧 wheel 可试（**有 wheel ≠ 官方承诺支持 sm_37**）；
- FlashAttention 要 sm_80+；某些 Qwen Engine 预编译 CUDA wheel 明确要求 **cc 7.5+ / CUDA 12.8**，K80 被排除在外；
- 官方 `qwen-tts` Python 示例写的是 `dtype=torch.bfloat16` + `attn_implementation="flash_attention_2"` —— **K80 两个都不满足**，原版 PyTorch 路线基本走不通（改 FP32 + eager + 旧版源码构建属未验证，E）。

**能走的（C，社区实测）**：llama.cpp 的 Kepler fork（`CMAKE_CUDA_ARCHITECTURES=37`、CUDA 11.x、关 CUDA Graphs / FlashAttention / NATIVE）在双芯 K80 上实测跑过 20B MoE Q4（~16GB）和 26B A4B Q4（~20GB），BF16 权重回退 FP16 cuBLAS。**这是社区 fork，不是官方支持。**

**最稳的（B）**：qwentts.cpp 自带 **CPU 后端**（GGML），GGUF 在 CPU 上一定能跑，跟 Kepler 无关。K80 那台机器的 CPU 就够用——你说「不在乎速度」，正好把这条慢路消化掉。

**结论**：K80 能跑的是 **GGUF 路线**，不是官方 PyTorch 路线；「显存装得下」不等于「有官方支持」。而且 1.7B 本来就小，**K80 的价值不在装更大的 TTS，在做对照实验**。

> 未找到证据（E）：qwentts.cpp 的 CUDA 后端在 sm_37 上编译/跑通的公开记录；Qwen-Audio-3.0-TTS 的 GGUF；K80 上跑通原版 qwen-tts PyTorch 的案例。

## 五、研究回来，我的想法

### 判断 1：语义不在音频这一侧

「谁在说话、这句话该多悲伤、哪里该叹气」是**语言理解**，归 4B；「用这条嗓子、按这条指令把字变成声波」是**声学实现**，归 1.7B。Alexandria 用 `speakers / text / style / non-verbals` 的完整脚本 + 二次审校，Antioch 用 `speaker / text / voice instruction` 直接喂 qwentts.cpp——**两个同类项目都把 LLM 当导演、TTS 当演员**，这两份源码就在我们 `reference/` 里躺着。

我们现在的导演（4B abliterated Q4_K_M）真机上 10 分钟吐 0 条有效标注。换一个更会演的演员，救不了一个不写戏的导演。

### 判断 2：K80 最该当「离线标注工厂 + 盲听台」，不是当第二个手机

**不改 App 一行**就能用上「不在乎速度」：

1. **K80/PC 上跑更强的 LLM**（14B/32B Q4，llama.cpp Kepler fork 或纯 CPU 都行）把小说标成结构化脚本——不是现在「回显 500 字再切 JSON」，而是 **「区间号 + 谁说的 + 情绪强度 + 起止/衰减 + 非语言事件」的骨架**，切句和归属交给程序（Antioch 那条现成路）。
2. 导出 JSON → 手机 App 导入 → **用现有 1.7B GGUF 合成**。App 只加一个「导入标注」入口，JNI / 权重 / 无网络权限都不动。
3. 同一段文本在 K80 上用 qwentts.cpp 跑 **Q8_0 / BF16 / F32 / CustomVoice** 四组 WAV 盲听，先回答「量化档和模式到底有没有可听差别」，再决定值不值得动 App。

这样「不在乎速度」全花在语义层，收益可测，且不破坏端侧硬约束。要走「PC 产出音频再导入手机」也行，但那就不是 App 内合成了，局部重做、改人设、试听都会变麻烦，我不推荐当主链路。

### 判断 3：契约比模型便宜

把 `instruct` 从「平稳叙述」升级成可执行的表演指令：情绪名 + 强度 + 起止/衰减 + 节奏重音 + 非语言事件 + **稳定 voice card**（`角色 → 音色描述` 只读目录，别让 4B 每段重写人设，这正是「每小段音色不一样」的根）。Alexandria 的 `style` 与 `[gasps]` 分层、Antioch 的逐行 voice instruction 都是现成件。

⚠️ `intensity=0.72` 这类数值，Qwen3-TTS 官方接口**不承诺解析**，先用在调度层（分段、插静音、换 instruct），别当新咒语塞给模型。

### 判断 4：现在不推荐换引擎

我们连「4B 标注有没有真进到声音里」都还在等真机判定卡。这时候去移植 GLM-4-Voice / VoxCPM，是在没验证过的地基上再盖一层，而且要把 JNI 重写一遍。

## 六、证据分级与订正

| 结论 | 等级 | 依据 |
|---|---|---|
| 1.7B 会结合 instruct 与文本语义自适应 | A | Qwen 官方博客、HF 模型卡 |
| 只有 0.6B/1.7B，1.7B 是顶配；voicedesign 仅 1.7B | A/B | 官方模型矩阵、GGUF README |
| 86 行内标签属另一代闭源 API | A/B | 阿里云百炼、官方发布、CSDN 区分说明 |
| 换非同家族 GGUF 需重写引擎 | B | qwentts.cpp 源码结构、GGUF README |
| K80 双芯各 12GB / sm_37 / 无 BF16 / CUDA 12 不支持 | B/C | NVIDIA、CUDA 发行说明、GPUDojo |
| Kepler fork 实测能跑 20B Q4 | C | 第三方 fork README，非官方 |
| MiniCPM-o 4.5 支持 llama.cpp 量化 | D | 二手百科，待核 |
| qwentts.cpp CUDA 在 sm_37 可跑 / 3.0-TTS 有 GGUF / K80 跑原版 PyTorch | E | 未找到证据 |

**订正三条**：
1. 以前把 Qwen-Audio-3.0-TTS 的 86 标签泛称「下一代模型能力」→ 实锤**闭源 API、无权重**，不能本地部署。
2. 底稿写「MiniCPM-o 无官方 llama.cpp 路径」，我另搜到二手资料称 4.5 支持 llama.cpp/Ollama CPU 推理与多量化 → 标 **D 待核**，不作为落地依据。
3. 底稿把 Qwen3-TTS 归为「非端到端」；官方称 *Universal End-to-End Architecture*，但那说的是**语音生成路径端到端**（离散多码本，绕过 LM+DiT 级联），不等于「端到端语言理解」。两种「端到端」别混。
