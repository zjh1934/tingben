# 双模型配合 · 研究回来后的想法

> 2026-11-04 · R21 插队轮。底稿是 `双模型配合与日志可观测_调研.md`（多源核实，含「未找到」标注），
> 关键两条又自己回官方仓库复核过。本文只写**判断与取舍**，不复述调研报告，也不改代码。

## 0. 先纠一个我以前说得太满的地方

我之前把「小模型被要求回显平行 JSON 数组会陷入重复循环」当成已证实结论到处引用。
核实结果：Antioch `annotator.rs` 注释里**确实有这句工程判断**，但调研**没有找到** Qwen3-4B / 4B-abliterated 的
第三方基准实测报告。以后它只能当**风险假设**（解释我们真机「吐 1676 字不收敛」的一个候选），
不能写成「官方/实测证明」。这类「源码注释 ≠ 论文结论」的区分，后面每轮都要守住。

## 1. 音频模型到底吃哪一套

官方把三条路径做成**互斥的输入契约**，不是同一组参数的开关：

| 模式 | 必需 | 可选 | 不该混 |
|---|---|---|---|
| VoiceDesign（我们手上这个） | `text` + `instruct` | 语言、采样、长文分块 | `speaker`、参考音频 |
| CustomVoice | `text` + `speaker`（Vivian / Ryan 等 9 个） | `instruct` 作风格 | 参考音频 |
| Base | `text` + 3 秒参考 WAV | 参考文本 | 固定 speaker 表 |

**结论一：`speaker` 在 VoiceDesign 下不承载身份。** 官方 CLI 表写 `--instruct` required、Reference audio 不要求；
qwentts.cpp 架构文档把「voice_design 但 instruct 为空」列为 `INVALID_PARAMS`。我们代码里恒传 `speaker=null`
是对的，不是漏接。诊断日志「音色表 0 个」不是 bug，是这个模式的正常返回值。

**结论二：instruct 该写什么，官方有样板。** Qwen 中文资料给的是**整段自然语言**，维度覆盖
性别 / 音高 / 语速 / 音量 / 清晰度 / 流畅度 / 口音 / 音色质感 / 情绪 / 语调 / 性格；
示例原文如「以极度悲伤、带着明显哭腔的语气，用较小的音量缓缓诉说，语速缓慢……声音颤抖而压抑」。
英文模型卡样例是 `A deep, resonant male voice speaking with a calm and authoritative tone.`
所以**身份层 + 表演层拼成一条 instruct 字符串**是对路的，别去猜不存在的字段。

**结论三：seed 不是音色锁。** 固定 seed 只保证「同权重、同库版本、同 prompt、同文本、同分块」下采样可复现；
VoiceDesign 没有 speaker embedding，每次 synthesize 都按 instruct 重新采样。R19 的默认身份锚点 +
身份词剥离是**收敛漂移**，不是根治。想彻底同声线，得换 CustomVoice 用固定 speaker id —— 换权重、重下 2GB、
真机重验，用户没点头不做。

**结论四：感情能到哪。** 语气 / 快慢 / 停顿 / 哭腔 / 颤抖 / 气声，靠 instruct 引导，官方示例支持。
但 `[gasp]` `[laugh]` 这类**行内标签是 Qwen-Audio-3.0-TTS（另一代）的能力**，12Hz VoiceDesign 官方资料里
没找到支持证据；我们 prompt 里禁方括号是对的。这个权重也**没有** `speed` / `pitch` 独立字段——
「1.2 倍速合成」物理上做不到，播放端倍速 ≠ 合成端变速。叹气笑声目前只能靠 `NonVerbal` 给原文已有的
哭/笑/叹描写追加导演指令，正文一字不改。

## 2. 语言模型怎么调教

三道闸门，各管一件事，别混：

1. **模板层关思考**：Qwen3 官方 `enable_thinking=False` 硬开关；关闭时 `/think` 软开关无效。
   非思考档推荐 temp 0.7 / top_p 0.8 / top_k 20；思考档 temp 0.6 且**禁用贪心**（会无限重复）。
   我们默认关思考、快速档贪心，方向对；真机上 abliterated 权重的 chat template 仍可能吐 `</think>` 残片，
   所以解析层强制按闭标签裁剪要保留，不能只信模板。
2. **语法层**：llama.cpp 有 `llama_sampler_init_grammar`（本地 `llama.h:1527` 确认存在），GBNF 能强制合法 JSON。
   但它**只守语法壳**，不保证 `text` 逐字等于原文，也不保证模型不提前 EOS 或填满预算。
   GBNF 是「少产废话」的工具，不是「保真」的工具。
3. **业务层**：字符级 gate 才是最终裁判。放宽它就是换契约；要么严格保真，要么明确改编并补 `check_text_loss`。

**我现在对 4B 的判断**：让它一次干「复现全文 + 切分 + 归属 + 写指令」四件事，是失败的根源之一，
不是禁令写得不够狠。Antioch 的做法是把切分/归属交给确定性代码、LLM 只写 5~8 词指令；
ReaderVoice-Mobile 也把显式引语、用户锁定、两人交替等确定性问题挡在 LLM 之前。
**更稳的形状是让 4B 输出「可验证的骨架」**（原文区间 / 片段 + speaker + instruct），程序按偏移重建，
而不是要求它把 500 字一个不差地回显一遍。这是路线 B，值得做，但要动切分、缓存、gate、评测集，
按用户「改一处联动很多处」的纪律，单独一轮，不塞进改文案的轮次。

## 3. 两个模型怎么配合（我的结论）

**分层，而不是加长上下文：**

```
原文 → ① 确定性规则（章节/引号/角色字典/用户锁定）
     → ② 4B 只处理语义残差（谁说的、此刻怎么说）
     → ③ 程序校验（逐字 gate + 规则审计 + 失败码）
     → ④ TTS 执行（身份 instruct + 表演 instruct + seed → 24kHz WAV）
```

接缝现在是**断的**：4B 标出的 `speaker` 只是文字标签，没接到音色；全局/角色描述是通过
`VoiceProfile` 拼进 instruct 影响声音，不是按角色切声线。所以「多角色」目前仍是「一个声音演所有情绪」。

**三条候选路线，按代价排：**

- **A（本轮已做）**：不动模型，把「到底标了没有、长度对不对、规则生没生效」全部可观测。
  先有测量再谈优化 —— 否则换模型、调 prompt 都是盲改。
- **C（小成本）**：接 GBNF 语法约束 + prompt hash 进缓存主键。只减少语法废话，不碰保真契约。
- **B（中成本，最值钱）**：4B 输出区间骨架，程序重建原文。省的是「回显全文」这一大块 decode，
  对 9 秒/token 的手机最实在。代价是偏移归一化、重叠/缺口检测、缓存格式全改。

**明确不做的**：为了「角色不飘」去扩滚动 KV 上下文。每块都清 KV 是有意为之 —— 窗口 4096，
模型看得到前块反而容易把前块字混进本块 JSON，逐字 gate 直接失败。跨块连贯靠
「角色表 + 最近 3 条 + 紧邻前因」拼进 prompt 更便宜。真要补，优先把「最近 3 条」改成
「最近 3 块各取首尾 + 别名表」，纯改字符串。

## 4. 日志怎么设计（本轮已落地，详见 `日志重设计_标注审计.md`）

调研给的最有用一条：**日志记流水线事件，不记模型原始输出；常态摘要与诊断态详情分开**。
照这个思路但贴合听本：主事件流格式保持不变（`ts | KIND | ACTION | detail`），另开一份带 level
与结构化字段的诊断态日志；每块落一条可查审计（条数 / 长度 / 差异偏移 / 9 条规则 / 失败码 /
产出截取片段）；崩溃前 200 行环形缓冲写进 crash 文件。用户怀疑的「跑半天啥也没标」，
现在会直接变成 `ANN_EMPTY` 告警 + 汇总里的「零标注 N 块」。

## 5. 下轮按序做什么

1. **先测量**：装新版跑试音短篇，看 `ANN_RAW / ANN_AUDIT / AUDIT_SUMMARY`，记录每块
   decode token 数、耗时、重试率、失败码分布。**没有这份数据不换模型、不换 prompt 大结构**。
2. **P1② 前台服务 + PARTIAL_WAKE_LOCK + 通知**（本轮被插队顺延，仍是下一轮第一件）。
3. **C：GBNF + prompt hash 进缓存主键**（单独一轮，牵动 bucket / TaskResume / realProgress）。
4. **B：骨架化标注**（单独一轮，牵动切分 / gate / 缓存 / 评测集）。
5. 角色→音色映射真正接进合成；CustomVoice / Base 换权重留到用户明确点头之后。

## 6. 物理限制，写进产品前提

- 两个模型不能同时驻留（2.5GB + 2GB，8Gen3 必 OOM），所以「全标完 → 释放 LLM → 再合成」是结构，不是偷懒。
- nCtx=4096 是硬上限；CPU 9 秒/token、TTS RTF≈17 是这台机器实测，调参救不了。
- 24kHz/16bit/mono 固定；长书中间 WAV 要按章清理，只留审计清单，不做无界缓存。
- Android 15 起前台服务约 6 小时超时，设计目标永远是「到点停 + 回来点继续」，不是「永不死」。
