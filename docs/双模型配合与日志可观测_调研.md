# 双模型配合与日志可观测调研

## 摘要

Qwen3-TTS 官方把三条音频路径明确分开：VoiceDesign 必须传 `--instruct`，不应同时传说话人参考；CustomVoice 用 `--speaker`，`--instruct` 只作可选风格；Base 用参考音频和可选参考文本。因此 VoiceDesign 里传 `speaker` 是参数语义冲突，而不是“音色更稳”；`seed` 决定可复现采样，但官方文档没有承诺它跨多次合成锁定同一身份。官方确认 12Hz 编码和描述式控制，但没有找到 2026-11-04 可直接访问的官方文本明确列出“`[gasp]`、`[laugh]`”等为受支持的行内标签，故不应视为 VoiceDesign 契约；Qwen-Audio-3.0-TTS 的 86 种行内标签和 12.5Hz 不能自动外推到 12Hz VoiceDesign。语言侧最稳的组合是 `enable_thinking=False`、明确关闭思维开关、JSON Schema/GBNF 约束语法，再由听本自己做字符级拼接校验；GBNF 只保证语法，不保证回显原文。推荐采用“规则优先＋小上下文 LLM＋候选/规范状态分离＋逐 chunk 审计”的接缝，而不是无限扩充 4B 的输入窗口。

## 一、音频侧输入契约：VoiceDesign 是描述式路径，不是“speaker＋instruct”叠加

**已核实事实（核实日期：2026-11-04）**

Qwen3-TTS 官方模型页面把任务分为 Base、VoiceDesign 和 CustomVoice。Base 做零样本语音克隆，需要参考音频，可用可选参考文本；VoiceDesign 用自然语言指令创建声音，不需要参考音频；CustomVoice 使用模型内置说话人 ID。三者不是同一组参数的不同开关，而是不同的输入契约。[1] 官方 CLI 表进一步写明：VoiceDesign 的 `--instruct` 是 required，输入中没有 Reference audio；CustomVoice 的 `--speaker` 是 required，`--instruct` 为空时仍可工作；Base 的 `--voice-ref` 是 required。[1]

| 模式 | 必需输入 | 可选控制 | 不应混用 |
|---|---|---|---|
| Base | `--text`、参考 WAV | 参考文本、语言、长文参数 | 与固定 speaker 表叠加 |
| CustomVoice | `--text`、`--speaker` | `--instruct`、语言、长文参数 | 另传参考音频 |
| VoiceDesign | `--text`、`--instruct` | 语言、采样、长文参数 | `--speaker`、参考音频 |

`qt_tts_params` 的 qwentts.cpp 架构文档列出了两个自相矛盾的组合：`--speaker` 与 `--ref-wav` 同时给出，以及 `model_type == voice_design but --instruct empty or missing`；前者总是互斥错误，后者返回 `QT_STATUS_INVALID_PARAMS`。文档还说明，`--ref-wav given but model_type != base` 同样属于无效模式。这里的证据来自 qwentts.cpp 架构文档，不是 Qwen 官方仓库正文；听本应把这些视为“实现层错误规则”，上线前用目标 commit 的 `qwen.h` 复测一次。[2]

VoiceDesign 的输出格式已经由 qwentts.cpp 的 `qt_audio` 说明固定为 24kHz、单声道浮点 PCM；每次合成后必须调用释放函数。架构文档还写明采样链为 `repetition_penalty -> temperature -> top_k -> top_p -> softmax -> multinomial`，并说明 `philox_uniform_fill` 使固定 seed 能跨运行字节级复现。[2] 官方 CLI 共享参数表也把 `--seed` 列为“未给定则随机”，其余默认值为 `do_sample=true`、`temperature=0.9`、`top_k=50`、`top_p=1.0`、`repetition_penalty=1.05`。[1] 这是 TTS 自身的采样参数，不是 llama.cpp 的 sampler。

`instruct` 的“允许内容”在官方 VoiceDesign 模型卡里有自然语言示例：`"A deep, resonant male voice speaking with a calm and authoritative tone."`；这是 2026-11-04 找到的官方中文可检索资料中最接近“官方示例原文”的英文样例。[3] Qwen 官方博客的中文样例则覆盖音色、人设、情绪和表现强度，例如“展现悲苦沙哑的声音质感，语速偏慢，情绪浓烈且带有哭腔，以标准普通话缓慢诉说”。[4] 合理且保守的输入层应把 instruct 拆为“身份描述（性别、年龄、音色、口音）”和“表演指令（情绪、语速、语气、语境）”，但最终仍受模型训练分布控制。官方没有找到一份公开的、逐项枚举“允许写 X、禁止写 Y”的黑名单；因此，把政治人物克隆、仇恨表达、违法指令、冒充特定在世人士等列入产品侧禁写规则，属于产品安全判断，不是已核实的官方禁止清单。

官方 VoiceDesign 模型卡说明其支持从自然语言描述生成全新声音，并用 `language`、`instruct` 控制生成。[3] Qwen3-TTS 技术报告摘要确认该系列采用描述式控制，可创建全新声音并细粒度操纵输出语音；其 12Hz tokenizer 采用 12.5Hz、16 层多码书设计，支持低延迟流式。[5] 但摘要没有承诺 VoiceDesign 必然复现任何给定声音。听本应该把“同一角色固定同一身份描述＋同一 seed”作为可复现实验条件，而不是身份保证。

**推断（明确标注）**

VoiceDesign 的 `instruct` 在 qwentts.cpp 架构中被描述为进入 talker prefill 的自然语言描述；转换说明还称 VoiceDesign talker 没有固定说话人嵌入。由此可推断：`speaker` 字段在该模式下没有承载身份的作用，传与不传都不足以稳定控制音色，反而可能增加解析或校验风险。[2][6] 同理，身份层和情绪层分开拼装主要提升可维护性和可检索性，不代表 TTS 内部一定按两个独立潜变量处理。

`seed` 固定能让采样链复现，前提是同一模型权重、同一版本推理库、同一 prompt 组装、同一语言设置、同一文本和同一 codec 分块策略；任何一项改变，都不能指望输出波形逐字节相同。[2] 因此，手机上更现实的目标不是“永久同音色”，而是“同一角色/同一 run/同一参数时减少漂移”，并以角色 profile 哈希、seed、模型 SHA-256 和推理库 commit 做审计。

**未找到或未确认**

- 未找到 Qwen3-TTS 12Hz VoiceDesign 官方公开文档明确支持 `[gasp]`、`[laugh]`、`[sigh]` 等行内标签。Qwen-Audio-3.0-TTS 的 86 种行内标签、笑声/咳嗽/呼吸/叹气支持不能当作 12Hz VoiceDesign 的已核实能力。[7]
- 未找到 VoiceDesign 支持独立 `speed`/`pitch` 字段。官方参数表只列语言、采样、长文分块和 max-tokens；语速/情绪应通过自然语言 instruct 表达，效果需实测。[1]
- 未找到官方明确写出 `speaker` 在 VoiceDesign 下“非法”或会被忽略；目前能确认的强证据是“两者语义冲突”和 qwentts.cpp 的 `INVALID_PARAMS` 规则。[1][2]
- 未找到 VoiceDesign 的逐字符文本改写保证；生成可懂度属于模型能力，不应由 prompt 替代听本的字符级 gate。

## 二、语言侧调教：语法约束、思考关闭与字符级校验是三道独立闸门

**已核实事实（核实日期：2026-11-04）**

Qwen3 官方最佳实践明确：thinking 模式推荐 `temperature=0.6、top_p=0.95、top_k=20、min_p=0、presence_penalty=1.5`，不要使用贪心解码，因为可能性能下降并无限重复；non-thinking 模式推荐 `temperature=0.7、top_p=0.8、top_k=20、min_p=0、presence_penalty=1.5`。[8] 官方聊天模板支持 `enable_thinking=True/False`：关闭时不会输出思考内容；当总闸为 false 时，消息中的 `/think` 软开关无效。[9] 因此“默认关思考”是正确方向，但硬开关应放在模板层，并保留发生异常时强制裁剪 `<think>` 的解析逻辑，因为不同 llama.cpp 版本对 abliterated 模型 chat template 的实现可能不一致。

llama.cpp 的 GBNF 是输出语法约束机制；官方指南明确它能强制合法 JSON，也可限制为 emoji 等语法。[10] 当前 llama.cpp 接口暴露 `llama_sampler_init_grammar(model, grammar_str, grammar_root)`，同时有 penalties、top-k、top-p、temperature、grammar 等采样节点；grammar 在采样链末端遮蔽非法 token。[11] `llama-cpp-python` 的 `response_format={"type":"json_object"}` 或 JSON Schema 会在上层转换为语法约束；这只是便利封装，并不意味着模型理解“业务主键”或“必须与原文逐字相同”。[12]

KV cache 接口方面，llama.cpp 公开 `llama_kv_self_seq_*` 系列，包括复制、分段、移位和删除序列，`llama_kv_self_seq_keep` 会丢弃除指定序列外的内容；KV cache 按序列/位置管理，并可配置精度与自动碎片整理。[13] 对逐块处理而言，真正的物理边界是 4B 的 nCtx=4096：提示模板、规则、最近原文、目标原文和 JSON 输出必须共用这个窗口。KV 复用能减少前缀重复 prefill，但不能创造额外语义容量；旧 KV 删除后，旧 token 信息在普通全注意力实现中不再可见。

**推断（明确标注）**

“小模型被要求回显平行 JSON 数组时易陷入重复循环”在本调研中没有找到 Qwen3-4B 或 4B abliterated 的项目实测报告，故不能列为已核实结论。可以作为风险假设：目标文本已含大量引号、标点、相同角色名和结构化样板，若只给“逐字回显所有原文”的弱约束，模型在临近输出预算时确实容易延续模板；但这是根据训练样本模式、重复惩罚与停止条件作的工程推断，不是官方或第三方项目实测。

更稳的顺序应是：先让模型生成最小、封闭语法的 JSON；再用程序从原始章节按索引/偏移重建，而不是要求模型完全负责拼接。也就是说，让 LLM 输出 `(start_offset, end_offset, speaker_candidate, instruct)` 一类骨架，或者输出被原文区间验证过的子串，不把“全文无损回写”全压给生成模型。其代价是要写偏移归一化、重叠/缺口检测；但这比无限扩上下文、反复重试 JSON 更符合 CPU 端侧的现实。

**未找到或未确认**

- 未找到 llama.cpp 官方保证“贪心＋GBNF 一定收敛”。GBNF 可限制合法 token，但模型可能提前 EOS、填满预算、卡在允许前缀或无法找到满足业务约束的完成；仍需 max-tokens、停止符、重试和 JSON 修复上限。
- 未找到 4B abliterated 模型在 `enable_thinking=False` 时仍输出 `</think>` 残片的统一复现报告；这是版本兼容风险，不是已核实事实。
- 未找到官方说明“每 500 字是最优块大小”。块大小应由中文字符与 chat template token 数实测决定，而不是固定 500 字。
- 未找到 KV cache 复用在“逐段不同模板前缀”场景下的零成本证明；听本需记录每次复用的 prefix hash、seq id、保留位置和被移除区间。

## 三、开源项目的接缝：规则先跑，LLM 只处理语义残差

**已核实事实（核实日期：2026-11-04）**

Antioch 是最直接的对标：Rust CLI，使用 llama.cpp（Qwen3.5-2B GGUF）标注，再由 qwentts.cpp 合成；流水线为 Markdown→纯文本段落→带 `speaker`、`text`、`voice instruction` 的脚本 JSON→逐 chunk WAV→带可配置静音间隔的合并音频→可选 M4B。[14] 它的断点续跑单元是 chunk WAV：目录中已存在音频就跳过，不需要重新生成音频；这把“标注/重新标注”与“重新渲染”分开。[14] Antioch 为 MIT 许可证。[14] 这条链说明“一段文本对应一个音频文件＋一个 voice instruction”是成熟实现，而不是必须一次合成整章。

ReaderVoice-Mobile 是端侧 Android 语境下的另一参考。其设计明确“规则优先”：显式引语、用户覆盖、两人简单交替、当前场景排除等确定性问题不进 LLM；只有低置信才交给 ReaderDirector。上下文不传整章，而传当前段、最近 5–20 段、场景参与者、相关身份证据、已确认别名和用户覆盖，典型为 1k–4k token。[15] 它还把 Identity Memory 与 Performance Memory 分开：身份可以吸收未来证据，表演状态只能使用当前时间点以前的信息，避免未来剧情污染早期朗读。[15] 仓库描述其产品状态为“TXT→canonical 章节→语义→角色档案→持久化剧本→本地 TTS”，canonical chapters 是唯一产品口径；数据层采用 runs 中的候选集合与最终 canonical 结果分离。[16] 该仓库的公开搜索结果没有稳定给出可核实的开源许可证，故不应假定为 Apache-2.0、MIT 或可商用。

Alexandria 是 GUI 化有声书生成器，流水线为 Settings→Script→Voices→Editor→Result；它允许 Review Script 做二次 LLM 审校以修复说话人归属，脚本生成后自动检测说话人，并为每个角色建立 Voice Card，也支持别名共享同一声音配置。[17] 其默认提示偏英文，并明确建议中文书籍修改提示以适应中文对话约定；推荐非思维链模型生成脚本，列出 Qwen3 非思维链变体等选项。[18] 许可证为 MIT。[18] 它的价值在于把“角色生成”和“脚本审校”作为独立 pass，而不是让同一模型在一次输出中同时完成全部工作。

MultiActor-Audiobook 使用“多模态说话人画像生成（MSP）＋基于 LLM 的脚本指令生成（LSI）”，向 TTS 输入“语音样本/面部图像/说话指令”。公开摘要显示其说话指令包含音色画像和情绪表现，例如“An albino Caucasian teenager…”与“With a tone of deep frustration and sadness, the words are spoken softly, almost to oneself.”；该工作是首尔国立大学的研究原型，搜索结果未找到可核实的开源仓库或许可证，不能作为可直接集成的库。[19]

**推断（明确标注）**

对听本最值得借鉴的不是换一个更大模型，而是把工作拆成三层：第一层是确定性解析（章节、引号、已有角色字典、用户锁定角色），第二层是 4B 的轻量上下文预测，第三层是程序校验。ReaderVoice-Mobile 的“15 个失败码＋fail-closed”和 Antioch 的“chunk 文件存在即跳过”都说明，可恢复性来自明确状态，而非更长 prompt。[14][15]

角色→音色卡的映射建议在 VoiceDesign 下保存“角色 ID、身份 instruct、表演 instruct 模板、seed、禁止改写标志、参数哈希”，而不要只保存一个自由文本 prompt。这样同一角色的不同情绪可以共享身份描述、只替换表演层；代价是 profile 维护成本上升，但可审计性显著改善。若 qwentts.cpp 实例每次只接受全局 voice instruction，则“身份/情绪分层”只是配置层优势，不能宣称 TTS 内部会把两者解耦。

非语言事件应作为独立事件对象，例如 `{type:"nonverbal", event:"laugh", duration_ms:?}`，并保留 fallback。在 VoiceDesign 没有官方行内标签证据前，不要把它们直接插入正文或假设 TTS 会合成；更稳的做法是跳过、占位或另建音效层，并记录“事件未合成”。这与 Alexandria 的说明一致：非语言声音同样继承标注模型的失败模式，误判可能比平淡朗读更明显。[20]

**未找到或未确认**

- novel-voice-studio、ebook2audiobook 在本次可访问资料中未找到足够详细、可核实的 LLM→qwentts.cpp 接缝代码或许可证，不能写成已核实案例。
- 未找到这些项目对“小模型回显平行 JSON 时无限循环”的公开实测报告。
- 未找到任何项目官方承诺可改写原文；听本的物理契约应保持原文文本不变，最多允许规范化空白/标点，并将结果视为候选而非可替代原文。
- Antioch 虽使用 Qwen3-TTS，但默认 LLM 是 Qwen3.5-2B；不能据此推断 Qwen3-4B abliterated 在 4K 上下文内具有相同 JSON 收敛表现。[14]

## 四、端侧长流水线日志：事件可关联、逐块可审计，但不把模型噪声写入常态摘要

**已核实事实（核实日期：2026-11-04）**

Android `android.util.Log` 提供 `VERBOSE=2`、`DEBUG=3`、`INFO=4`、`WARN=5`、`ERROR=6`、`ASSERT=7` 六级，并提供 `Log.d`、`Log.i`、`Log.w`、`Log.e`、`Log.v` 及带 `Throwable` 的重载，也提供 `isLoggable(tag, level)`。[21] 这些是平台基础能力，而不是“可见即可用”的 UI 方案。Android 的本地 logcat 在发布环境还受系统版本、运行权限和崩溃后缓冲回收限制，故关键结果应额外落持久化审计文件。

llama.cpp 的日志可分级，例如其常见前端在 `-lv 4` 时进入 trace；但不同版本常量名和默认级别不同，听本不应依赖某个固定 tag 字符串，而应封装 JNI/前端日志回调并在构建时记录实际版本。[22] 生产环境建议常态只显示 info/warn/error 的汇总，trace 只在诊断页手动开启，避免每 token 输出刷屏。

**推断（明确标注）**

“看得清但不刷屏”的最小事件模型应为流水线事件，而不是模型原始输出：一次推理产生一条 `block_start`，模型完成产生 `block_end`，解析产生 `parse_result`，gate 产生 `gate_pass/fail`，TTS 产生 `tts_chunk`，合并产生 `merge_result`。每条事件都携带 `run_id、book_id、chapter_id、block_id、attempt、model_key、model_sha256、backend_commit、ctx_size、params_hash、elapsed_ms、status_code`。音频 chunk 输出文件可直接作为旁路证据，无需在日志里复制全部 PCM。

建议设置两级事件：

| 级别 | 常态记录 | 不应记录 |
|---|---|---|
| 用户态摘要 | 章节、块范围、段数、字符数、耗时、状态、失败码 | 正文全文、模型原始输出、异常完整 stack 全部展开 |
| 诊断态详情 | 模板摘要、token 估算、KV 保留/移除、采样参数、重试轨迹、原始 JSON、gate diff | 每次 decode token、重复进度条、JNI 内部调试 |

每次 `block_end` 应计算：输入原文长度、拼接后长度、精确字符差、分段数量、空结果数量、JSON 合法性、是否触发思考清理、是否走 fallback、4B 耗时、TTS 耗时、输出样本数。若拼接长度不等于原文长度，记录首个差异偏移，而不是把整段原文写进日志；诊断页可按用户操作导出有限窗口的原文片段与 JSON。

零标注/空结果应被定义为显式业务失败码，例如 `EMPTY_ARRAY`、`NO_OBJECTS`、`CONCAT_LEN_MISMATCH`、`CHAR_OFFSET_GAP`、`JSON_SYNTAX_FAIL`、`GRAMMAR_TIMEOUT`、`THINK_TAIL_NOT_CLOSED`。空结果不能静默直读；至少写入“输入哈希＋失败码＋已尝试次数＋降级动作”。崩溃前保存固定大小环形缓冲，例如最近 200 个流水线事件、最后 10 个 block 摘要、最后 3 次失败 payload；保存时截断模型输出，并在 UI 诊断页允许用户一键复制纯文本/分享脱敏文件。

## 对听本的具体建议

**零成本（不改模型、不改 JNI 也可在 Java/Kotlin 层落地）**

1. 立即把 VoiceDesign 调用拆成“身份 instruct＋表演 instruct”，两者都保存在角色 profile；但在 API 层先拼成单个 `instruct` 传入，不要额外猜字段。删除所有 VoiceDesign 路径下的 `speaker` 参数。
2. 固定 `seed` 与模型/库版本，并把角色 profile 哈希写入审计事件；不要宣称 seed 能锁定身份。可先对同一角色的 10 个相邻块做 A/A 复现测试，量化音色漂移。
3. 建立四级结果状态：`PASS` 字符级相等；`RECOVERED` 可修复但已记录；`FALLBACK` 直读；`FAIL` 不产出音频。每一次都要记录失败码、首个差异偏移和尝试次数。
4. 日志只常态显示每块“输入/输出长度、段数、耗时、状态、失败码”；trace 用诊断开关控制。诊断页可一键复制最近 run 的脱敏摘要，不默认导出正文。

**小成本（主要改进 prompt、状态机、缓存和重试边界）**

1. 把 4B 的任务从“回显全文”改成“输出可验证的标注骨架”：优先返回原文片段或章节内区间，再由程序拼接；GBNF/JSON Schema 只保证语法。
2. 将输入上下文压到典型 1k–4k token：规则先识别确定引语和锁定角色，只把当前段、最近少量段、场景参与者、候选别名和覆盖项给模型。这比维持巨量 KV 更现实。
3. 加独立的二次 review pass：第一遍标注，第二遍只核对不确定角色和高风险情感块，而不是整章重做。Alexandria 的 Review Script 可作为设计参照，但不能照搬其模型规模。[17]
4. 用“规则结果＋4B 候选”的两态结构持久化，canonical 结果只来自通过 gate 的候选；直读块也要有固定文件/状态，可重跑但不再占模型算力。
5. 每次 TTS 请求保存 chunk 文件和输入哈希；崩溃或取消后按块跳过已完成音频，但重新校验 canonical 脚本，避免旧音频与新标注错位。

**要换模型（只有在基础测量证明 4B 是瓶颈后再做）**

1. 当前 CPU 上 4B 的死循环/跑半天问题没有第三方实测证据；应先记录 token/s、每 500 字耗时、重试率、失败码，再决定是否换更小 non-thinking 模型、更严格 grammar 或更大模型。不要根据单次异常推断模型能力。
2. 若目标是稳定 JSON，可评估非思维链、较小模型＋更严格 schema 的链路；Antioch 用 2B 作参考，但设备、模型和 TTS 都不同，不能直接证明其一定更快或更稳。[14]
3. 若目标是音色稳定，优先验证同一 Qwen3-TTS 变体在固定 seed/profile 下能否满足听本，而不是简单增加模型尺寸；尺寸不能消除 VoiceDesign 无 speaker embedding 的架构事实。[6]
4. 若必须换 TTS，应选择允许说话人 reference 或稳定 speaker ID 的模式，并重新建立量化、RAM、热缓存和加载时间的基线；不要把 Base/CustomVoice 的身份能力误当成 VoiceDesign 的现有能力。

**物理限制必须作为产品前提**

8Gen3 的 CPU 推理速度不是无限的：4B 与 1.7B TTS 不能同时长期驻留时，必然存在加载/卸载或内存压力；这不是日志能修复的问题。nCtx=4096 是硬上下文上限，规则优先和小上下文是适配该上限，而不是临时 workaround。24kHz/16bit/mono 的输出文件体积和逐 chunk PCM 拼接使长书会产生大量中间数据，应按章节清理中间 WAV、保留审计清单，而不是无界缓存。若以后引入非语言音效、重采样、多轨混音，磁盘 I/O、RAM 和 CPU 都会成为新的瓶颈，应在架构层保留输出采样率与量化参数的不可变记录。
