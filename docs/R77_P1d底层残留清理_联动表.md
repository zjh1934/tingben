# R77 · P1d 底层残留清理 · 联动表（落地前先列）

**2026-11-06 · 基于 `1.1.0+74`（run 74）源码实读**

R76 把「角色音色」幽灵页从界面删掉，但**底层仍在跑**：`Prefs.voiceStamp` 里还含角色表 hash，
`Pipeline` 合成循环还逐段查角色表，`CastPresets.kt` / `VoiceCast.kt` 两个文件还挂着。
本轮把这些物理清掉，界面一行不改。

## 一、为什么不能「直接删 hash」

`voice_stamp.txt` 存的是上次合成时的指纹。旧算法是四项：

```
sha( "4" || voiceDesc || (castEnabled ? sha(cast.json) : "off") || knobs.hash() )
```

删掉角色表那一项 → 新指纹值变了 → `Pipeline` 的 `stampFile.readText() != voiceStamp`
判为「声音配置变了」→ **把用户已经做好的所有 WAV 一次性删光**。这是 R76 故意留着的原因。

**迁移方案（双指纹兼容）**：新增 `Prefs.legacyVoiceStamp(c)`，用旧四项算法算值（不依赖将被删的
`VoiceCast.kt`，把 `cast.json` 的读法内联成私有函数）。比对改成：

```
changed = old != voiceStamp && old != legacyVoiceStamp(c)
```

- 旧手机：stamp 文件是旧算法值 → 命中 legacy → **不作废**，只把文件改写成新值
- 已迁移 / 新装：stamp 文件是新值 → 命中 voiceStamp → 正常
- 用户真改了音色描述或采样：两个都不等 → **照常作废**（这是预期行为，不能被兼容逻辑吃掉）

`cast.json` 从此**只读一次**（仅迁移比对），不再写入、不再 reconcile、不再 resolve；
不主动删用户文件，留着是一个不再被访问的空数据。

## 五、如实说

- 这轮**界面零改动**，用户看不出变化；价值是代码里不再跑角色表、旧音频不会被误删。
- `cast.json` 作为历史数据不主动删除；`legacyVoiceStamp` 是过渡兼容读，等全量用户迁移完
  可在后续版本删，本轮不假装「一次清干净」。
- 真机帧率 / 手感仍是零证据，按新纪律不向用户索取装机验证。
