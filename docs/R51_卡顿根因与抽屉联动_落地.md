# R51 · 卡顿根因收窄 + 抽屉从「覆盖」改「联动」· 落地报告

> 本轮**不进 V2**（目录页 / 按章绿勾 / 看书页 / 迷你条一行未动）。
> 用户问句：「为什么这么小的软件用起来这么卡？界面切换卡得要死」「抽屉应该是左滑展开收起、和右边工作页有联动，不是覆盖」。
> 结论先行：**不是软件小就该快，是高频状态挂在整棵页面树的根上、页面全量组合、还跑着三个无条件定时器；抽屉用的是官方覆盖式组件。**

## 一、卡顿：查出来的，不是猜的

| # | 根因 | 证据 | 本轮处理 |
|---|---|---|---|
| ① | 为 5 个**根本没用**的参数，把高频状态挂在整棵树根上 | `App()` 顶层 `Producer.state/resume.collectAsState()`；`LibraryScreen` 函数体对 `producing / progressText / onProgress / pendingTask / onTasks` 零引用。制作时每次块更新重组 `when(screen)` 下全部 9 页 | 删 5 参 + 2 个顶层订阅；`KeepScreenOn()` / `TaskBar()` 各自在叶子订阅；续跑回调读 `.value` 不订阅 |
| ② | 9 页全是 `Column + verticalScroll` | 无论多少子项一次性全量组合 + 测量 | **未改**：改 `LazyColumn` 会破坏 R50 的 `onGloballyPositioned` 锚点语义，9 页一起动风险过大，单列性能二期 |
| ③ | 三个无条件定时器 | 音频页 300ms tick（闲着也 3.3 次/秒整页重组）、任务页 1000ms tick + `tick/2` 每 2 秒读盘、进度页 1000ms 无条件 | 音频页改 `LaunchedEffect(pq.isPlaying)` + 500ms；任务页合成一次 2 秒 `loadTick`；进度页按 `st.running` 门控 |
| ④ | 组合期同步读磁盘 | 各页 `remember(refresh) { BookStore.list / AudioLibrary.list / VoiceCast.load }` 在主线程解析 JSON | **未改**：要改 `produceState` + 空态，牵动 9 页，单列 |
| ⑤ | 装的是 debug 包 | `isMinifyEnabled=false`、带 `androidx.ui:tooling`；官方明确 debug 关闭 Compose 编译器优化 | **未改**：换 release 会动签名/CI/7 个 .so 闸门，单列 |

另：`MixerScreen` 的 `snapshotFlow { scroll.value to anchors.toMap() }` 每滚动一帧复制整张锚点表 → 改成流里只放 `scroll.value`，表在 `collect` 里现读，语义不变。

**所以「这么小的软件」不成立**：APK 18MB，但 Composition 树有 9 页、几百个控件，且引擎每次更新把整棵树重算一遍。本轮修的是**确定的结构性浪费**，不宣称卡顿归零。

## 二、抽屉：覆盖 → 联动

**改前** `ModalNavigationDrawer`：官方语义是盖在内容之上 + 全屏遮罩，右边工作页纹丝不动 —— 就是用户说的「覆盖」。
**改后** `DismissibleNavigationDrawer`：官方 standard drawer 展开时**把右侧工作页一起推走**，不用手搓手势、不用自己算 offset。

守恒：☰ `drawerState.open()`、从左边缘右滑 `gesturesEnabled=true`、返回键优先收抽屉、7 个目的地、`requiredWidth(240.dp)`、底部 `navigationBarsPadding()` —— 一行未改。`AppDrawerSheet` 仍用 `ModalDrawerSheet` 作样式容器，`@OptIn(ExperimentalMaterial3Api::class)` 兜住 M3 实验性标记。

## 六、如实限定
