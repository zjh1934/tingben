# 听本后台保活与浮窗调研

## 总判断

**两个想法都不成立。** 无障碍服务不是保活 API，其官方目的仅是辅助残障用户使用设备和应用；申请权限既不会进入前台服务状态，也不会获得免杀、免 Doze 或更高 `oom_adj` 待遇，反而会把离线推理 App 置于 Google Play 非辅助用途治理与 Android 13+ 受限设置风险中。[1][2] `SYSTEM_ALERT_WINDOW` 浮窗也不是前台服务：Android 明确要求前台服务必须显示状态栏通知，而显示浮窗并不会自动申请前台服务、不会阻止 Doze、也不会稳定提升 LMK 优先级；若浮窗由后台弹出且不与可见 Activity 或前台服务配合，其可见性可能不被计入「用户可感知」。[3][4] 对用户锁屏后「模型到底能不能活」的准确回答是：**系统层级由前台服务、电池优化策略、Doze/App Standby、LMK 及 OEM 后台策略共同决定；App 层级则由前台服务类型、可见通知、唤醒锁、检查点和设备设置共同决定。** 在本项目离线、无网络权限的硬约束下，正确目标不是追求「永不死」，而是做到「前台服务可续跑、每完成一块就落盘、被杀后可无网准确恢复」。

## 一、后台执行与进程存活的决定链条

**前台服务是 Android 给出的唯一正规长任务承载方式，而不是某个隐藏 API。** Android 官方把前台服务定义为「执行用户可注意到操作」的服务，且必须显示无法自行关闭的状态栏通知；例如音乐播放器用它播放音轨，健身应用在获得许可后记录跑步数据。[1][5] 对听本而言，这正意味着「后台跑模型」应当被建模为用户主动开始、持续可见、可随时取消、结果进入本地音频库的工作，而不是一个悄悄保活的计算任务。前台服务的通知标题和进度应真实描述当前状态，如「正在离线合成第 312/1280 段」，而不是伪装成播放通知以骗取用户信任或规避系统分类。

**`START_STICKY` 只表达被杀后的重启意愿，不是存活保证。** 系统可能在内存恢复或后续组件启动时重新创建服务，但不会因此免除电池优化、后台启动限制、前台服务类型校验、Doze 或 OEM 管理策略。尤其 Android 12 起，后台应用通常不能在任意时刻自行调用 `startForegroundService()`，合法入口主要是：用户从可见界面显式启动、现有前台应用转交、PendingIntent、近期交互等路径；具体边界会随 target SDK 和场景变化。因而，听本应在用户点击「开始制作」时从 Activity/前台界面启动 FGS，而不是等进程已到后台后再偷偷启动。

**锁屏后真正起作用的并非一个开关，而是四层机制叠加。** 第一层是前台服务类型和可见通知；第二层是 `PowerManager` 唤醒策略；第三层是 Doze/App Standby 与应用待机分桶；第四层是低内存时 LMKD 依据 `oom_score_adj` 与应用重要性选择回收对象。Android 官方将进程重要性分为前台进程、可见进程、服务进程、缓存进程等层级，前台服务属于「可感知」而非普通后台服务，但这仍不意味着绝对不被杀。[6] LMK/LMKD 属于设备内核与 ROM 实现，具体阈值、厂商调优和进程分级会有差异，不能写死某个 `oom_adj` 数字。

**Doze 会在设备未充电、静止且灭屏一段时间后延迟 CPU 工作，并明确忽略常规唤醒锁。** Android 官方文档称，Doze 会暂停网络访问、推迟标准 AlarmManager 闹钟、不允许同步适配器和 JobScheduler 运行，并且「忽略唤醒锁定」；App Standby 则在用户未主动使用应用、没有前台进程等条件满足时判定应用空闲。[7] 因此，`PARTIAL_WAKE_LOCK` 最多帮助维持 CPU 唤醒，绝不能被描述为「防止锁屏被杀」。听本若长时间持有唤醒锁，还可能在 Android Vitals 中被标记为过度唤醒锁；公开的质量指标说明是，单个用户会话若 24 小时内累计持有超过 2 小时非豁免唤醒锁，就会被视作过度。[14] 这并不等于必须放弃唤醒锁，而是说明它应仅覆盖真正需要连续 CPU 的推理块，并按「每个块开始—结束」及时释放，不能从首次点击一直持有数小时。

| 机制 | 对听本的作用 | 能阻止什么 | 不能阻止什么 | 判定 |
|---|---|---|---|---|
| 前台服务 + 可见通知 | 声明用户可感知的长任务 | 被系统识别为 FGS、降低普通后台限制 | 不能免除超时、电池优化、OEM 冻结 | 确定 |
| `PARTIAL_WAKE_LOCK` | 避免 CPU 在短时等待中休眠 | 覆盖部分 CPU 休眠 | 不阻止 Doze、LMK、OEM 清理 | 确定 |
| 电池优化白名单 | 让应用进入较少限制的 App Standby 分桶 | 减少部分待机限制 | 不是免死金牌，不替代 FGS | 确定 |
| 任务卡片锁定 | 在最近任务里保留入口 | 可能降低用户手动清后台的概率 | 不影响系统 LMK 策略 | 推定，OEM 相关 |
| 无障碍服务 | 辅助交互/读屏 | 无 | 无保活授权 | 确定 |
| 浮窗 | 观察/快速操作 | 无 | 无保活授权 | 确定 |

## 二、前台服务类型：本项目最接近 `dataSync`，但不宜自封系统豁免

**`dataSync` 是最接近本项目的类型，但它是数据搬运/处理语义，不是系统豁免。** 官方前台服务类型页面将 `dataSync` 描述为数据传输或处理，并要求声明 `FOREGROUND_SERVICE` 与 `FOREGROUND_SERVICE_DATA_SYNC` 权限；Android 15 起它还具有约 6 小时的超时边界，目标版本升级后会按新版行为执行。[8] 听本逐块生成 24kHz WAV 并处理本地模型结果，可以描述为「用户主动发起的本地数据生成」，与 `dataSync` 更接近；但「更接近」不等于自动合规，必须在通知、代码和提交说明中如实表达，不能宣称自己在进行网络同步。

**`mediaPlayback` 不适用。** 该类型的语义是播放可感知的媒体内容。听本虽然最终产出音频文件，但当下正在做推理与合成，并非正在播放一首用户可听媒体；若已经生成一段可播放音频，播放环节当然可以另用媒体会话/播放器，但长耗 CPU 的合成阶段不能借用 `mediaPlayback` 规避 `dataSync` 的超时。把通知写成「正在播放」而实际在跑推理，会构成用户误导和系统类型误用。

**`specialUse` 不能用来补漏洞。** 它要求提供自定义用途，并在应用清单中给出能被审核者理解的说明，通常面向无法纳入既有类型、且平台认可的特殊场景；Google Play 仍可审查并拒绝。听本已有相对明确的本地处理语义，不应为了「绕过超时」跳到 `specialUse`，更不应把本地推理包装成无关用途。

**`systemExempted` 与本项目无关。** 它面向系统应用或具备系统级豁免资格的场景，普通第三方应用不应申请。任何把 `systemExempted` 列为「让小米不杀后台」的公开教程，都不足以作为听本实施依据。

**Android 15 的约 6 小时上限不是「六小时后数据丢失」，而是服务必须重新回到用户可见/合法状态。** 若任务超过上限，听本应依靠既有的逐块落盘与任务书签，在通知中明确「已完成 X/Y，恢复后将继续」，由用户重新确认后从前台界面启动下一轮 FGS。对于几小时的合成任务，这并不比「一直假装运行」更差，反而更符合 Android 的资源治理模型。Android 16 还进一步按应用活跃度、可见性变化和前台服务绑定动态限制后台任务时长，继续压缩了把 FGS 当作无限计算槽的空间。[15]

**小米/HyperOS 的额外行为不能由设备型号反推。** 小米官方公开资料能确认 Android 版本层面 HyperOS 3 基于 Android 16，但不能据此断言型号 24117RK2CC 的每一项后台策略；「神隐模式」「自启动」「省电策略无限制」等具体入口与默认行为还会随 HyperOS 版本变化。[10] 因此本报告把具体 OEM 判定标为**待核**，只能通过真机实验与官方版本公告确认。可执行的检测项是：应用信息中的自启动、电池/省电策略、后台运行/后台活动、通知/常驻通知、悬浮窗、锁屏显示、最近任务卡片锁定。对用户文案应写成「在系统设置中允许本任务在后台运行」，附版本相关说明；不应硬编码未公开的 Activity 或反射调用。

## 三、AccessibilityService：辅助用途的 API，不是进程优先级 API

**官方设计目的非常窄。** `AccessibilityService` 的 API 说明首句即为「无障碍服务应仅用于帮助残障用户使用 Android 设备和应用」；其生命周期由系统管理，用户必须在设备设置中显式开启，服务可由用户关闭或自行调用 `disableSelf()`。[2] 它没有「提升宿主进程优先级」的契约。普通 Android 组件是否被视为前台，官方依据是可交互 Activity、前台服务、系统绑定服务等条件，而不是是否启用了无障碍服务。[9]

**无障碍会监听系统和界面事件，这与本项目的纯本地推理需求并不匹配。** 听本不需要读屏、自动点击、界面遍历或替用户操作其他应用。若仅为「保活」启用无障碍，等于让一个高敏感服务持续运行、读取窗口事件，并承担不必要的权限解释、用户教育和隐私沟通成本。Android 13 起，受限设置会影响不可信安装来源应用启用无障碍服务，用户可能看到「此设置当前不可用」之类限制；即使通过可信渠道分发，非辅助功能用途仍会面临治理风险。[11]

**若申请无障碍，不能将 `isAccessibilityEnabled` 当作优先级探测。** 这个状态只能说明某个无障碍服务是否启用，不能推导 `oom_adj`、是否在前台、是否免 Doze，更不能预测小米会不会冻结进程。实际实验中可能会观察到某台设备「开启后没被杀」，但这是相关性：系统、内存状态、其他设置或测试时长都可能变化，不能据此建立因果结论。

**Google Play 风险的核心不是 API 名字，而是功能主张。** 官方无障碍 API 与 `isAccessibilityTool` 体系要求开发者准确披露无障碍用途；2017 年以来 Google 已明确限制以非辅助用途申请或保留 Accessibility API。听本如果自称有声书制作工具，却启用无障碍服务且不提供读屏、输入替代、界面交互辅助等真实无障碍功能，商店审核可能要求证明辅助价值，甚至拒绝或下架。Android 17 的高级保护模式又进一步强化非无障碍工具使用无障碍 API 的限制，说明这个方向是继续收紧而非放宽。[16]

| 替代方向 | 是否适合听本 | 说明 |
|---|---:|---|
| 前台服务 + 进度通知 | 是 | 正规承载长任务 |
| 任务页 + 原子书签 + 检查点 | 是 | 被杀后恢复，是真正可靠性来源 |
| WorkManager | 仅适合边界明确、可中断的工作 | 本地大模型持续 CPU 工作并不自然适合标准后台约束 |
| 无障碍服务 | 否 | 只能用于真实辅助功能，不保活 |
| 自启动/厂商白名单引导 | 有条件 | 让用户主动设置，不伪装用途 |

## 四、SYSTEM_ALERT_WINDOW 浮窗：可以观察，不能替代前台服务

**浮窗权限与前台服务权限不是同一体系。** `SYSTEM_ALERT_WINDOW` 是特殊敏感权限，需通过 `ACTION_MANAGE_OVERLAY_PERMISSION` 引导用户进入系统设置手动授权；Android 11 起该 Intent 会把用户带到顶级管理页面，包名参数不再保证跳到应用专页。[12] 它允许应用在其他应用上方显示窗口，但不自动授予 `FOREGROUND_SERVICE`，也不意味着系统会把应用视为前台应用。

**浮窗的可见性不等于 Activity 处于前台。** 如果浮窗依附于一个后台服务或已 `onStop()` 的 Activity，系统仍然会按实际组件状态管理进程；Android 8.0 起还会在前台存在叠加窗口时显示通知提醒。[13] 反过来，如果浮窗在 Activity 处于前台时显示，那主要因为 Activity 在前台，而不是浮窗本身提高了进程等级。搜索结果中所谓「有悬浮窗就在前台」只是对厂商定制或旧版本行为的二手描述，不能替代官方进程重要性定义。[9]

**「浮窗 + FGS」比「只有 FGS」多的是用户观察和快速操作，不是稳定性。** 前者仍需要 FGS 及其可见通知；浮窗可以提供暂停、取消、展开查看进度、跳转任务页等入口，但任何启动 Activity 的操作都必须遵循后台启动 Activity 规则。Android 12 起还可由其他应用调用 `setHideOverlayWindows()` 隐藏应用叠加窗口，说明浮窗本身还会被系统和其他应用主动约束。[17] 因而，浮窗应采用 `TYPE_APPLICATION_OVERLAY`、明确尺寸、非遮挡式设计，并在 Activity 销毁后及时移除窗口，避免泄漏或在锁屏/输入密码界面制造 UX 与安全风险。

**OEM 对浮窗的控制不可忽略。** Android 官方规定了窗口类型和权限，但厂商可能在权限管理、省电策略、锁屏显示、后台弹出界面等层面对其额外管控。小米公开页面不足以证明所有 HyperOS 版本对浮窗有一致的冻结或放行规则，因此应标为**待核**。建议真机检查四个状态：仅 FGS、FGS + 可见 Activity、FGS + 浮窗、FGS + 用户主动打开浮窗；记录进入时间、结束时间、中断原因与最近一次书签，而不是仅凭「有没有被杀」下结论。

| 方案 | 锁屏后稳定性 | 用户透明度 | 结论 |
|---|---:|---:|---|
| 仅浮窗 | 不比普通后台更好 | 中 | 不做保活方案 |
| 仅 FGS | 明显高于普通后台 | 高 | 主路径 |
| FGS + 用户主动打开的浮窗 | 与 FGS 基本相当，可能略好或受 OEM 影响 | 高 | 可做观察面板 |
| FGS + 自动隐藏浮窗 | 不确定 | 低 | 不建议，增加权限/被判定滥用风险 |
| 无障碍 + 浮窗 | 不因此提升 | 低 | 不建议 |

## 五、浮窗指标可行性：内存可看，GPU 利用率不能当稳定产品指标

**App 自身 Java/Kotlin 内存可以较可靠地获取。** `Debug.getMemoryInfo()` 与 `ActivityManager.getProcessMemoryInfo()` 适合观察本进程或指定 PID 的 PSS、private dirty、native heap 等字段；`Runtime.totalMemory/freeMemory` 只能反映 Dalvik/ART 堆，不能代表 llama.cpp、qwentts.cpp 的 native 占用。官方内存调试文档把 `dumpsys meminfo`、Perfetto、堆转储等作为调试工具，但 App 内读取通常优先使用 SDK 的 `MemoryInfo`。[18]

**系统全局 CPU 使用率可以通过 `/proc/stat` 计算，但属于非公开稳定契约。** 可在后台线程解析 `/proc/stat`，保存前后两次采样和时间差，按 `(all_cpu_time_delta - idle_delta) / all_cpu_time_delta` 计算整机 CPU 利用率；要区分 CPU 占用来自本进程还是系统，应结合 `/proc/self/stat`、线程目录或 native CPU profiler，而不是把整机 CPU 直接标成模型占用。这些 proc 文件在 Android 上通常可读，但不同内核、SELinux、加固 ROM 可能改变可见性或字段顺序，因此只能标为**能拿到，需做解析容错与版本防御**。

**设备温度/每核 CPU 存在 API，但是否实现是 OEM 问题。** `HardwarePropertiesManager` 的官方参考列有 CPU、GPU、电池、皮肤温度，`getCpuUsages()` 提供每核 CPU 使用信息，`getFanSpeeds()` 提供风扇转速；官方页面没有明确普通第三方应用的额外权限要求，也未必保证每台设备实现。[19] 在 Xiaomi 24117RK2CC 上，应先用 `PackageManager.hasSystemFeature()` 或 `getSystemService()` 判空并捕获异常，字段为空时隐藏面板，不能假定数据一定存在。

**GPU 利用率没有公开稳定的统一 API。** Android SDK 没有面向普通应用提供「GPU 使用率百分比」字段。Vulkan/Adreno 的 perfcounter、debug marker、层、扩展属于驱动或厂商能力，通常需要开发者选项、root、系统签名、隐藏 API 或 OEM 授权，不能在生产浮窗中作为承诺指标。能获取的是 GPU 温度（前提是 `HardwarePropertiesManager` 实现了对应传感器），以及从 `dumpsys gfxinfo`、`dumpsys gpu` 等系统服务读取的调试信息——但后者需 `adb shell`、shell/签名权限，且输出随版本变化，普通浮窗不能稳定调用。

**把浮窗做成高频轮询会反向增加耗电。** 若在 Activity 中使用 1 秒一次的 `Handler` 轮询，即使浮窗很小，也会持续唤醒主线程、解析 proc 文件并触发 Compose 重组。建议默认 2–5 秒刷新、进入后台或设备息屏后降到 10–30 秒或暂停，由 FGS 的进度回调而非 UI 轮询驱动模型状态；只在用户展开面板时启用更细粒度采样，并允许用户在浮窗设置中关闭实时刷新。这样能把「观察」与「让模型活着」彻底解耦。

| 指标/接口 | 本机可行性 | 说明 | 判定 |
|---|---|---|---|
| App PSS/native heap | 能拿到 | `Debug`/`ActivityManager`；不依赖 root | 确定可用 |
| 整机 CPU 利用率 | 通常能拿到 | `/proc/stat` 两次采样计算；非公开稳定 API | 推定 |
| 本进程 CPU 时间 | 通常能拿到 | `/proc/self/stat` 或 `/proc/self/schedstat`；需解析 | 推定 |
| 每核 CPU 使用率 | 部分设备 | `HardwarePropertiesManager.getCpuUsages()` | 确定 API，厂商实现待核 |
| CPU/GPU/电池温度 | 部分设备 | `HardwarePropertiesManager` | 确定 API，传感器待核 |
| 风扇转速 | 部分设备 | 同上；手机通常无风扇 | 确定 API，实用性低 |
| GPU 利用率百分比 | 稳定公开 API 不存在 | Vulkan/Adreno 多为隐藏或厂商接口 | 确定 |
| `dumpsys gfxinfo` | 需 shell | 不适合普通前台浮窗 | 确定 |
| 通过浮窗降低模型占用 | 不能 | 显示不等于调度 | 确定 |

## 六、对听本的具体建议

**P0：先做「可恢复」，再谈「不杀」。**

1. 新增一个职责单一的 FGS：仅执行「标注块 → 校验块 → 合成块 → 原子落盘 → 更新书签/通知进度」，不做 UI、网络或无关工作。服务类型优先评估 `dataSync`，通知如实写为「本地有声书制作」。
2. 用户从任务页或播放前点击「开始制作」时，从可见 Activity 调用 `startForegroundService()`；服务必须在超时窗口内调用 `startForeground()`，通知必须可见且可取消任务。
3. 复用现有逐块落盘和原子任务书签，为每块增加可验证的哈希或至少写入完成标记，恢复时跳过已完成块，不重复播放、不重复消费算力。
4. 在 FGS 内按块申请/释放 `PARTIAL_WAKE_LOCK`，禁止整轮数小时常驻；锁屏进入 Doze 后的行为应在真机上测量并记录，而不是假设锁不会被释放。
5. 恢复路径完全离线：任务页读取本地书签与块状态，显示「上次完成到第 N 块，是否继续」；无需联网、无需账号、无需上报。
6. 不做自动重启伪装。被杀后返回任务页明确显示恢复点，由用户确认继续；若系统允许并确实能启动，再考虑显示可操作的恢复通知，但不承诺自动续跑。

**P1：让用户主动打开浮窗，且不扩大权限边界。**

1. 浮窗放在设置页中，默认关闭；只有用户明确开启时才请求/跳转 `ACTION_MANAGE_OVERLAY_PERMISSION`。不把浮窗设为自动弹出、不设置 1px 窗、不把浮窗作为保活开关。
2. 浮窗可显示：当前阶段（标注/合成/落盘）、块进度 X/Y、本轮累计耗时、App PSS、整机 CPU、GPU/CPU 温度（设备支持时）、「展开」和「暂停/取消」。不要显示拿不到的 GPU 利用率。
3. 展开浮窗时再打开任务详情；按钮只启动一个显式 PendingIntent/Activity。锁屏或安全界面下不弹出、不抢焦点。
4. 浮窗与 FGS 解耦：没有 FGS 时浮窗只能显示「当前无任务」；有 FGS 但没有浮窗权限时任务继续正常运行。
5. 真机覆盖测试中，至少记录 30 分钟、1 小时、2 小时、4 小时四档，以及在插电/不插电、亮屏/锁屏、内存压力高、后台运行其他大型应用等条件下的中断与恢复成功率。这是验证建议是否成立，而不是只截图证明「今天没被杀」。

**不做：无障碍保活、隐蔽窗口、系统豁免幻想。**

1. 不申请 `BIND_ACCESSIBILITY_SERVICE` 或启用 `AccessibilityService`；不因「进程监控」监听窗口与触摸事件。
2. 不申请与用途无关的权限；在无 INTERNET 硬约束下，不添加任何网络诊断、遥测、远程配置或自动恢复请求。
3. 不申请 `SYSTEM_ALERT_WINDOW` 仅仅为了占住窗口；不用 `systemExempted`、隐藏类型或反射厂商 Activity 绕过后台限制。
4. 不把 `START_STICKY` 写进产品文案，不承诺「保证后台运行到底」。
5. 不把合成过程伪装成媒体播放，不用虚假通知标题、静音播放器或循环音频换取类型分类。

**现有硬约束的冲突清单。** 无 INTERNET：排除远程日志、崩溃上报、商店自动恢复、云端模型；恢复只能本地重放书签。离线：排除需要联网证明的前台服务类型或商店验证捷径。不引新权限：排除把「关闭电池优化」当作强制前置，只能解释与引导；排除以浮窗、无障碍权限换稳定。不联网上报：浮窗采样只能保存在本机，可做导出调试报告但必须用户主动触发。不假装自动续跑：任务页应明确区分「自动恢复成功」「等待用户继续」「失败/文件损坏」，避免把用户主动恢复包装成系统后台续跑。

## 七、风险、合规与上架影响

**无障碍是本项目最高风险的错误答案。** 它的权限描述会涉及查看屏幕内容和执行操作，用户看到后会自然担心读取、自动化或隐私问题；如果听本没有任何辅助功能界面，却要求这个权限，信任成本远高于「用户允许后台」本身。Google Play 会审查 Accessibility API 的使用理由，公开政策沟通强调非辅助功能用途的限制；在 Android 13+ 侧载场景可能遇到受限设置，在 Android 16/17 高级保护等安全模式下也可能被进一步收紧。[11][16] 因此即便纯本地、没有联网，也不能凭「不收集数据」推导出无障碍合规。

**浮窗风险相对低，但前提是用途诚实。** `SYSTEM_ALERT_WINDOW` 会被系统提示为敏感权限，覆盖其他应用还可能触发 Android 8+ 的前台叠加通知。风险主要来自遮挡输入、频繁刷新、自动弹出、锁屏行为，以及用户误以为它在后台耗电。把它设计为小尺寸、可关闭、暂停/取消入口、按需展开，并在设备不支持时降级，能显著降低风险。它不应成为启动长任务的前置条件。

**小米安装/弹窗风险只能做版本化说明。** Android 官方没有统一规定小米每次开机、升级或权限变更必须弹出什么，具体授权弹窗和自动重置行为属于厂商实现，本报告标为**待核**。可做的防御是：启动浮窗前检查权限；失败时展示去系统设置的手把手路径；申请被拒后不影响核心功能；不要在循环里反复跳转权限页。不要在应用内声明「小米一定不会杀后台」。

**合规文案应描述事实而不是暗示豁免。** 推荐文案：「本地模型制作可能需要数十分钟至数小时；应用会以可见通知运行，并在每块完成后保存进度。锁屏或切换应用后，设备省电策略可能暂停任务；中断时可在任务页从已完成位置继续。浮窗仅用于查看本地运行信息，不影响任务能否继续。」不要写「无障碍让系统优先运行」「浮窗保证后台不断」「已关闭电池优化就不会被杀」。

## 八、常见误解

**「开了无障碍，系统就把我当前台应用」是错误。** 前台状态来自用户正在交互的 Activity、前台服务、系统绑定服务等，无障碍服务没有这种声明。[2][9]

**「无障碍 API 能提升 `oom_adj`」是错误。** 官方无障碍生命周期文档没有任何进程优先级提升契约；只读到一个启用状态不能推导 LMK 行为。

**「浮窗在屏幕上，所以进程是可见进程」是错误。** 浮窗可以由后台 Activity、普通服务甚至已离开前台的进程持有。可见窗口影响体验和部分系统判定，但不是 FGS 替代品。

**「有 `SYSTEM_ALERT_WINDOW` 就不用通知」是错误。** Android 明确要求前台服务显示通知；浮窗不能取代通知，反而可能额外触发叠加层提醒。

**「`START_STICKY` 能让服务永活」是错误。** 它只是被杀后重新启动的提示，不绕过 Doze、后台启动限制、类型超时和 OEM 策略。

**「`PARTIAL_WAKE_LOCK` 防止锁屏被杀」是错误。** Doze 明确忽略常规唤醒锁；唤醒锁只解决部分休眠问题，不解决内存压力、待机分桶和厂商冻结。[7]

**「关了电池优化就绝对不会死」是错误。** 电池优化白名单能减少 App Standby 限制，但不是系统级永久豁免；LMK、前台服务超时和 OEM 策略仍可能介入。

**「显示 GPU 占用就能降低 GPU 占用」是错误。** 读取指标只是观测。Android 普通应用没有稳定公开的统一 GPU 利用率 API，调度的真实杠杆是模型参数、线程数、精度、并发块数和系统资源管理。

**「本次没被杀，就是保活方案有效」是错误。** 一次成功只能证明当时设备、内存、温度和电源状态下存活；必须做多时长、灭屏、内存压力、恢复和跨版本测试。

## 九、结论排序与落地判断

**最稳：** 用户主动开始 → 前台服务 `dataSync` → 可见、可取消的进度通知 → 每块原子落盘与可验证书签 → 按块管理 `PARTIAL_WAKE_LOCK` → 被杀后在任务页由用户恢复 → 真机覆盖锁屏与长时长测试。这是唯一同时符合 Android 机制、离线约束和用户信任的路径。

**次稳：** 在上述基础上增加可选浮窗，作为用户主动开启的调试/观察面板，显示真实可用的 App 内存、系统 CPU、温度，隐藏 GPU 利用率与不可靠字段；浮窗只读取状态，不反向影响保活。该方案稳定性不高于「只有 FGS」，主要价值是信息透明和快速控制。

**不推荐：** 为后台保活申请无障碍；以浮窗、隐藏窗、1px 窗、虚假播放或隐藏服务维持可见性；申请 `systemExempted` 或 `specialUse` 规避分类；通过 root/隐藏 API 读取 GPU；把恢复功能伪装成系统自动续跑。它们既不改变前台服务与 LMK 的基本规则，又会增加权限、商店审核和用户信任风险。

**最终判断：无障碍对后台推理保活没有确定价值，反而会引入合规与安全风险；浮窗也没有保活价值，只适合观察。** 在 Xiaomi 24117RK2CC / Android 16 / arm64-v8a 上，能做到的最高可靠性是「前台服务续跑 + 本地检查点恢复」，而不是「永不中断」。具体小米策略因 HyperOS 版本无法由公开资料完全确定，仍须在本机完成测试并保留版本与实验记录。
