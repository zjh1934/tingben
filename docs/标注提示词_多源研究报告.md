# 端侧小说有声书流水线：4B 模型标注提示词设计与 prompt 改动的架构联动

## 摘要

对“听本”而言，最关键的结论不是让提示词更像导演，而是把逐字保真从模型任务改成**可程序验证的硬契约**：原文进、归一化原文出；输出先经字符级 gate，失败再修 prompt 或输入，而不是让 4B 多生成一遍“解释”。手机实测表明，一次 prefill 约 60～115 秒，生成约 9 秒/token，思考预算还会进一步挤占本已紧张的 4096 上下文；因此任何依赖长链思考、多轮 few-shot 或第二轮整块 review 的方案，都必须用分钟级成本换取收益，而不能按云端延迟设计。[1] 建议采用“确定性切分与并行句分割＋4B 只输出最小语义标签＋5～8 词短 instruct”的路线；它能显著降低输出长度和 JSON 收敛风险，但会牺牲跨句转折、次要说话人和细粒度情感连续性。结尾重申有效，但只适合作为最后一道提醒；最有价值的保真示范是一个目标块同形示例，而 WRONG/RIGHT 能压缩错误空间，却会消耗宝贵的上下文预算。llama.cpp 的 GBNF/约束解码适合守住 JSON 的语法骨架，不能保证 text 与原文逐字相同；Qwen3 官方思考开关则说明本地非思考模式更匹配“生成预算必须可预测”的端侧场景。[2] 最终必须把 prompt 版本、模型与量化、切分规则、角色表和语音资产写进缓存主键：只要其中任一契约变化，旧标注缓存原则上作废，只有内容与规则均被重新验证时才能复用。

## 1. 逐字保真不能交给复述能力，必须由程序做最终 gate

**真正能“逐字保真”的只有字符级校验，提示词只能降低失败概率。** 本项目的 JSON 元素是 `{"text","speaker","instruct"}`，其中 `text` 必须拼回原文。最稳妥的提示不应先写“禁止改写”，而应把原文同时定义为输入锚和输出模板：每个输出字符串都是源字符的连续子串，按出现顺序拼接后必须构成原文；模型不得替换同音字、繁简、全半角、标点、数字、省略号或引号，不得合并或拆开原文句子。随后再补三条禁令：不新增原文没有的字，不补全引语，不输出思考、注释、Markdown 或尾随解释。这样的顺序是从**可验证契约**到**负面清单**，比只列“不要改写”更具体，也更方便 gate 报错时映射 token 范围。

**结尾重申有用，但收益集中在收口而非纠错。** 当前 prompt 结尾再次要求“拼起来必须逐字相同”是合理的，因为它将生成任务的最终约束放在解码器最容易注意到的位置；然而模型在已生成数百 token 后，往往缺乏足够状态返回修正前文。所以结尾语应承担“结束并封口”的职责：直接写“只输出满足上述条件的 JSON 数组，不要解释”，而不是再次重复整段长规则。若结尾包含大段重申，会增加本就昂贵的 decode 预算，却不能弥补已经生成错误 `text` 的事实。

**few-shot 的核心价值是展示“同形输出”，不是展示文采。** 对本地小模型，最有效的是一个紧凑的 one-shot：输入原文若干行、短角色表、最近 3 条，输出一个与目标块形态完全相同的 JSON 数组；输出中所有 `text` 都直接取自原文，`speaker` 只有规范名，`instruct` 为 5～8 词。不要给一段几百字的小说再附一大段“标准 JSON”，因为 4B 会学到“复述输入”而不是“标注输入”。示例还必须覆盖本项目最高频的错误类型：带前引号未闭合的截断句、插叙旁白、同一角色连续发言、角色未出现在目标段但被提及。示例不能覆盖所有小说体裁，否则会把罕见文体会话错误固化为模板。

**WRONG/RIGHT 是强错误校正，但每次复用都会争夺 4096 token。** 一对反例可以把“把‘他道’改成‘他说’”“为对白补主语”“把三个短句合并成一个 `text`”等高频错误显式拒掉。建议只保留 2 条左右最高收益反例，而不是堆成训练集。每条必须保持极小：WRONG 一段错误 JSON 或错误文本，RIGHT 只改出错字段。反例放“规则之后、示例之前”，因为模型应先知道约束，再看到边界。当前 prompt 没有 few-shot 和反例，属于明确的改进空间；但公开资料没有针对“听本”这种 4B 端侧中文逐字标注的对照实验，因此只能依据契约设计、小模型容量和项目真机延迟判断，不能声称某组写法在该场景已有量化实证。

**重复循环与 echo 是提示缺陷的外显，不是单独的解码问题。** 真机曾出现 4B 输出 1676 字仍不收敛，说明当目标块较长、规则复杂、JSON 收敛路径过远时，模型可能反复生成相邻文本或重新复述原文。缓解方法不是增加 `max_tokens`，而是把预期输出长度显式上界化：例如“行数最多为目标段句号/感叹号/问号切分后的数量＋旁白合并上限”；同时 GBNF 强制 `text` 来自一个受控 token 集合时，约束本身也会缩小合法 continuation 空间。此处的代价是约束越复杂，每步候选集计算和采样变慢，且仍无法阻止 `text` 在语义上被错误地重复、拼接或遗漏。

## 2. 小模型应只做无法确定的归属与短指令，切分必须退出生成路径

**让 LLM 同时切分、归属并写长指令，是把多个故障域塞进一次昂贵生成。** 推荐路线是先由确定性代码读取原文字符流，按中文句末标点、引号边界和最大长度生成“候选边界”；再把每条候选交给规则分类器判断是否为对白或旁白。LLM 只接收一组已分割的行，输出与每行一一对应的 `speaker` 与 `instruct`，不负责决定每行从哪里开始、到哪里结束。这样做的好处是：`text` 可从程序侧直接引用原文切片，理论上不存在重新抄写；输出行数固定；JSON 的键、类型和数组长度可由 grammar 控制；decode 长度从潜在的数百字说明压缩到短标签，显著降低 9 秒/token 下的成本。

![一次 prefill 已足以消耗约一分钟，逐 token 解码成本不可忽视](/data/workspace/dr:31/fig_1_inference_budget.png)
*图 1：手机 CPU 上 prefill 与逐 token 解码预算。数据来源：用户提供的真机实测。*

**确定性分割并非万能，关键是保留“不可切边界”。** 中文可用“。”、“！”、“？”、“；”作为首选边界，“，”、“、”只在单行超过上限时降级；引号左右边界不能跨越，未闭合引号要带回到下一行；省略号、破折号、书名号和数字不得切碎。规则还应把独立说话标签“某某道”“某某问”“他想”作为**行级元数据或相邻行上下文**，而不是对白内容；否则 TTS 会把“张三冷笑道”朗读出来。对于古文、半文白、意识流、无标点文本和转述引语，规则会系统性失效，此时应回退到 LLM 的“归并与边界建议”，并将回退块单独打标、降低缓存复用优先级。

**输出应拆成“N 行并行预测”，而非“一个自由 JSON 数组”。** 可给每行单独任务：`id`、`start/end`（程序生成，不给模型编辑）、`dialogue`（布尔）、`speaker`、`instruct`。若坚持当前扁平数组，grammar 必须固定元素顺序，并显式允许数组长度上限。建议输出一个数组，其中每个对象字段顺序固定为 `text`、`speaker`、`instruct`；`text` 用受控原文 token、`speaker` 用角色表枚举、`instruct` 用受限自然语言。这样的设计能减少字段漂移，但 GBNF 对无界中文自然语言只能以“允许的汉字集合＋空格＋标点”描述，会扩大而非排除语义错误。

**剥离切分后，最适合把 LLM 输出降为短标签。** 当前每条 5～8 词的 instruct 可以作为中期目标，但提示应给出维度而不是开放创作：“意图或情绪、强度、节奏、重音、发声状态”。例如“压抑，中强，放慢，尾字加重，气声”“急切，强，加快，重读‘立刻’”“叙述，平，稳定，略停顿”。不要把整段人物小传或音色描述塞进每行，因为全局身份由 VoiceDesign 资产承担，逐行只描述此刻差异。

**这一路线的主要损失是“跨句连续性”与“复杂归属”。** 确定性代码无法理解反讽、旁白者模仿角色、多人抢话、心理活动与对白混合，也无法为十行连续的同一角色生成平滑的情绪曲线。适用条件是：正文标点规范、角色名相对规范、对白边界清晰、目标场景偏通俗小说。若项目想处理古典章回、意识流、网文对话密集或“只听声音就能听出转折”的高表现力作品，建议保留“整块 4B 预测”作为低置信度回退，而不是强制每行模型预测；置信度可由角色表覆盖率、前因后效一致性、规则冲突数和 gate 失败次数综合得出。

## 3. 中文对话归属必须把前因放在最显著位置，post-cue 只做异步复核

**目标段之前的上下文应占绝大部分预算，且越接近目标段越重要。** 角色表适合放在 prompt 前部，因为“首尾位置效应”研究显示，相关信息位于输入开头或结尾时性能通常较高，位于中间时会显著下降；该研究覆盖多文档问答和键值检索，而非小说标注，因此不能直接给出本项目的准确率数字，但足以支持端侧的位置设计。[4] 对“听本”，目标块前最近 3～8 个句子最能提供“谁正在说话、上一句是否未闭合、叙述者是谁”，应紧邻目标块。角色表只在前面出现角色频繁变化时才应完整保留；若上一块只有两个角色，压缩成“活跃角色＋其别名＋旁白”更有效。

**目标段之后的线索有效，但不应免费占 prefill。** 中文小说常用“……张三道。”收尾，因此后文能确认引号内容属于谁；这就是 post-cue。然而把目标块后面的整段原文放入主 prompt，会重复消费上下文、prefill 和生成预算。更适合端侧的做法是两级：先用目标段与前因做一次低成本确定性/小模型预测；若说话人不确定或引号跨越块边界，再读取下一小段有限窗口，只回答“当前未闭合对白最可能的说话人”，随后丢弃临时窗口。这个临时 pass 的输出不应进入主缓存的语义内容，只能用于修正当前边界。

**角色表必须是规范名＋别名＋稳定 speaker key 的映射，而不是人名列表。** 程序应把“张三”“三哥”“张兄”“他”在已知上下文足够时映射到规范名，但输出层可采用稳定的 `speaker_id`，TTS 映射则根据 id 取音色；这能避免同一角色因“张三/三哥”产生两个角色、也避免改 prompt 时 speaker 字符串变化而误认为新角色。主从标注并非必须：如果 TTS 仅按说话人分轨，单列 `speaker` 足够；若未来要让旁白按儿童/成年、可靠/不可靠叙述者采用不同演绎，才增加 `narrator_role` 等字段。当前没有证据表明“主次说话人”在 Qwen3-TTS 1.7B VoiceDesign 中存在原生双轨语义，因此应把它视作应用层标签，而不是 TTS 功能。

**sliding window 与 roster＋last-N 之间不是二选一。** 推荐 roster 存全书的规范角色、别名字典、活跃区间和 TTS 映射，推理上下文则只携带当前活跃子集；近期历史用 last-N，但对 N 的定义应是“若干完整语义块/句”而非“若干 token”。每次生成前按重要性排序：固定长度的目标块最高，紧邻前因次之，活跃角色表再次，远端历史最低。Qwen3-4B 官方声明原生上下文为 32K，但本项目主动把窗口限制为 4096；因此“模型支持 32K”不能用于证明当前任务能承受 32K，预算仍由真机 prefill 和手机资源决定。[2]

![4096 token 中目标块仅约 500 字，余量必须优先给前因与校验规则](/data/workspace/dr:31/fig_2_context_budget.png)
*图 2：上下文预算的分项约计。数据来源：项目现状与 4096 上下文；角色/提示/余量的字符与 token 换算须按真机 tokenizer 校准。*

**上下文摆放应做成可开关实验，而不是凭一句 prompt 定型。** A/B 组至少包括：只有目标块；目标块＋前因；前因＋post-cue 二级复核；角色全表＋前因；活跃角色子集＋前因。指标应分别记录说话人准确率、对白/旁白边界 F1、字符级文本损失、prefill 时间和生成时间。这里没有现成公开评测可直接套用，故所有结论均待真机验证。上下文预算数据可下载：[推理预算数据](/data/workspace/dr:31/data_inference_budget.csv)；[上下文预算数据](/data/workspace/dr:31/data_context_budget.csv)。

## 4. 本地 GGUF 的硬约束只在语法层有效，思考税会直接破坏端侧预算

**llama.cpp 可用 GBNF 约束 JSON，但不存在“自动理解 JSON Schema”的魔法。** 官方仓库提供 GBNF 语法说明，`llama.cpp` 的 `--grammar` 或等价 API 可按上下文无关文法限制每一步合法 token；也可使用项目内置的 JSON 辅助规则。对于本项目，建议明确数组元素顺序、字符串、逗号、空格与换行，并对 `speaker` 使用角色规范名枚举。GBNF 能阻止多余字段、错误类型、未闭合引号和 JSON 截断后的非法 continuation，却无法判断 `text` 是否来自原文、是否漏句、是否错误归属。

**JSON Schema 模式要区分后端支持与本地运行时能力。** OpenAI 的 `json_schema`/`strict` 是云端 API 能力，依赖服务端模型训练与动态约束解码；本地 llama.cpp GGUF 没有公开证据支持同名 API 会自动解析任意 JSON Schema。[5] 在 llama.cpp 中，正确路径通常是把 JSON Schema 转换为 GBNF，或手写一个足以描述输出形状的文法。具体版本差异须在项目所用 commit/Release 的 `grammar-json`、README 与参数帮助中复核；不能仅凭新版仓库支持就假定旧版 APK 内的推理库支持。

**`json_object` 模式通常只要求输出包含合法 JSON，不保证字段与业务含义。** 若本地 llama.cpp 编译版本提供类似 OpenAI 的 `response_format={"type":"json_object"}`，它最多保证“输出中有一份可解析 JSON”；仍可能输出错误字段名、额外对象、解释性前缀，或生成一个并不满足项目数组结构的对象。因此必须同时开 grammar、程序校验和业务 gate。云端 API 常见的“strict schema、tool calling、parallel tool calls、自动拒绝、动态 schema 编译”等能力，不能默认映射到 GGUF；尤其是 Qwen-Audio-3.x/qwen-audio 系列的行内角色/情绪标签能力，更应按具体版本的官方文档核对，不能把云端 API 能力写成本地 VoiceDesign 已支持。

**思考税不是抽象风险，而是本项目的时间预算。** Qwen3 官方文档确认混合思考模式可由 `enable_thinking=True/False` 切换，默认开启思考；其上下文长度虽声明为 32K，但本项目只能使用 4096。[2] 思考内容会先占用输入/输出空间，并延迟实际 JSON 出现。报告项目已观察到“推理吃光预算导致 JSON 被拦腰截断”，这与官方可控思考机制共同支持一个明确判断：**端侧 4B 标注默认使用非思考模式**，除非某一块被确定性校验标记为高风险，且项目愿意为一次慢速分析付出分钟级代价。没有证据显示关闭思考必然降低某种具体说话人任务准确率，所以“reasoning tax”在这里首先是延迟与截断风险，而不是已量化的质量结论。

**约束越硬，越要避免约束本身制造重复。** 若 grammar 对 `text` 使用过严的原文 token 集合，模型在候选少、原文又模糊时可能停不下或绕圈；若太宽，则失去意义。建议 grammar 只约束整体 JSON 壳与 `speaker` 枚举，把 `text` 的精确匹配交给代码：代码把目标块的归一化原文提供给模型，生成后再用原文子串查找/序列对齐验证。这样可以防止 GBNF 成为延迟和循环的新来源，也避免把“语法合法”误认为“文本无损”。

## 5. 指令必须拆成全局身份、行级变化和不可变的同步协议

**全局音色身份和逐段 instruct 应由两个独立变量承担。** 全局身份可以固定角色性别、年龄感、音质、声区、鼻音/胸腔感、咬字清晰度、典型语速和禁忌；它是 VoiceDesign 的声学/质地层。逐段 instruct 则只描述该行相对全局身份的变化：情境、意图、情绪状态、强度、节奏、重音、停顿与发声状态。两者若混在一个自然语言字段，TTS 会把“低沉男声”和“此刻气急败坏”同时重读，音色与情绪互相拉扯。更稳妥的做法是全局描述绑定到 `speaker_id`，每行只传 `instruct`，除非 TTS 接口明确支持“identity prompt＋direction prompt”双输入。

**5～8 词不是字数红线，而是延迟预算下的压缩目标。** 建议逐行 instruct 采用“情绪/意图＋强度＋节奏/重音＋发声状态”四槽：前两个决定“为什么这样说”，后两个描述“声音怎样变”。示例：“讽刺，强，拖长尾字，低气声”“疲惫，弱，断句，微沙哑”“震惊，强，骤停，提声”“平静叙述，中，稳定，清晰”。同义词不可随意扩展；项目应先冻结一份受控词表，否则 `instruct` 会漂移成散文，TTS 比较和缓存命中也会变难。

**逐行重复情绪状态大概率必要，但“必要程度”依赖 Qwen3-TTS 实际运行方式。** 若每行独立调用 VoiceDesign，上下文不会自然延续，前一句的“愤怒”无法自动约束下一句的“压抑”，所以情绪状态应重复；但声学身份若也每行重复，会增加输入并可能让模型重新推断音色。理想接口是全局 voice design prompt/参考音频固定身份，逐段自然语言指令只描述状态差。公开官方资料在本次可访问范围内未提供 Qwen3-TTS 1.7B VoiceDesign 的完整本地 GGUF 接口、字段名、token 限制和逐行指令继承行为，因此“全局＋逐行”应作为架构建议，而非宣称已得到官方确认；上线前必须根据所用 GGUF 的模型卡/README/推理代码验证。

**声学术语和行为术语必须分层，因为模型会做字面加权和。** “基频低”“气声”“鼻音”“慢 20%”是声学描述；“愤怒”“克制”“试探”是行为意图。前者适合 VoiceDesign 或稳定声学配置，后者适合逐段演绎。若将两者无结构地并置，例如“低沉男声、气声、愤怒、慢”，模型可能把每个词都解释为独立滤波器，甚至让“低沉”与“提声”冲突。建议模板先写行为意图，再写声学变化：“压抑质问（意图）→略降音区、气声、句尾加重”；若 TTS 不解析括号，可改用受控标签 `intent=压抑质问|acoustic=pitch_down,breathy`。这是工程推断，具体标签是否提高 VoiceDesign 遵循率，需项目做小样本盲听测试。

**全局指令也需版本化。** 一个全局 voice profile 至少包括模型来源、VoiceDesign 文本、参考音频哈希、采样参数、归一化规则和质量标签。改了任何一项，都不能只凭角色名复用旧音频；若仅改写不影响声学身份的描述，也要保留旧版与新版 id，避免同一角色在不同章节音质漂移。

## 6. 第二轮 review 的价值取决于能否复用 prefill，纯整块复核在 CPU 上通常不划算

**整块五修在手机上最危险的地方，是为一次不确定收益重新付出 prefill。** 若 Alexandria 的 five-fix 指剥离归属标签、拆分误归旁白的对白、合并过碎旁白、校验 instruct、check_text_loss，这些项目并非同等代价。字符级文本损失检测完全可以独立成程序：拼接输出 `text`、去除项目定义的空白/格式差异后与原文比较，直接报告漏字、多字、替换、顺序和偏移。这个 check 是本项目最便宜且最必要的第二遍，不应因“不想做 review”而被省略。

![第二轮整块复核会把约 100 秒单块成本直接翻倍](/data/workspace/dr:31/fig_3_review_cost.png)
*图 3：不同复核方案对 4B 调用次数的放大。数据来源：用户实测与成本模型；调用次数非实测准确率。*

**更便宜的替代是“稀疏、定向、只读”复核。** 第一层使用确定性规则：引号平衡、原文覆盖、字段类型、角色表枚举、行数上限、instruct 词表与长度。第二层只对高风险块调用模型，例如字符 gate 失败、说话人不确定、引号跨块、规则冲突或前因后效不一致；复核只输入出错行及极小上下文，要求模型只输出修复 diff。第三层对高价值书籍才做全量五修。与一次性让 4B 重读整块相比，这种方案可以保留第一次 prefill 的成果，只支付修复成本。

**当前的“重试一次再降级直读”是可用兜底，不是高质量策略。** 重试应带最小变化：只调整输出长度、解析方式、是否开启思考，以及当前块最近一条历史；不要在一次失败后随机大改角色表。若仍失败，直读必须保留原文与默认旁白音，同时记录 `loss_characters`、`loss_ratio`、`failed_rule` 和修复状态，不能静默降级。这样即使语音没有表现力，也不会产生 AI 改写的版权与事实风险。

**Alexandria 的 five-fix protocol 目前没有在本次可核验的一手资料中得到完整确认。** 本次检索没有找到可公开访问的 Alexandria 仓库、README、论文或明确列出上述五项的官方文档，因此“five-fix protocol”的具体步骤、顺序、项目归属和有效性均应标记为**待验证**，不能直接视为行业实证。本报告对该名称的使用仅来自用户描述，后续若找到源码，应将实际流程与本项目建议逐条对齐。

## 7. 改 prompt 是跨模块契约变更，缓存必须按内容寻址而非按章节序号

**prompt 改动会联动九个部件。** 第一，切块策略：若新增“心理活动”“旁白视角”“对白子句”字段，切分边界和最大长度必须随之变化；第二，标注缓存格式：输出 schema、版本号、字符偏移、角色 id、prompt hash 都要进入记录；第三，断点续传分桶：缓存应以原文内容哈希＋块内归一化规则寻址，不能只按章节/块号；第四，gate 校验：prompt 若改变允许空白、标点或引号的表示，校验器必须同步；第五，TTS 输入：新增 `emotion` 或 `prosody` 会改变 VoiceDesign 调用参数；第六，角色映射：若 speaker 从显示名改为规范名或 id，音色路由必须迁移；第七，事件日志：失败原因、重试次数、截断位置和直读兜底都要可追溯；第八，评测集：提示版本变了，旧准确率不能和新准确率混用；第九，用户体验：缓存重建会影响进度、流量、发热和电量。

**建议的缓存主键是内容寻址，而非文件名。** 主键可包含：原文规范化哈希、块起止偏移、语言/标点版本、切分规则版本、角色表快照哈希、prompt 文本哈希、模型权重/量化哈希、推理后端与版本、温度等采样参数、thinking 模式、grammar 版本、TTS profile 哈希。只要任一影响输出或声学的字段变化，key 就变化；只有关键字段未变、原文切片与规则完全一致时，旧缓存才可复用。对手机来说这会增加键长度和迁移工作量，但远小于错误复用导致的错角色、错情绪或错文本。

**作废规则必须分级，而不是“改一个字全量重标”。** 改动了文本归一化、原文切片、JSON 字段语义或 gate 规则，旧缓存内容一律作废；角色表只增加别名但规范 id 不变时，可继续复用，同时后台做归属回归测试；prompt 只改措辞而未改输出契约时，最好做小批 A/B 再决定；模型权重、量化、llama.cpp commit、thinking 模式或 grammar 变化，默认全部作废；TTS voice profile 变化不影响文本标注缓存，但必须让音频缓存失效。最保守也最稳妥的策略是：prompt hash 变化即视为文本标注缓存失效，除非有回归集证明输出分布和 gate 通过率无显著变化。

**断点续传必须区分“已生成”和“已验证”。** 生成完成不等于可播放：状态至少包括 raw_output、parsed、schema_valid、text_loss、speaker_mapped、tts_queued、tts_ok。崩溃恢复优先跳过 `schema_valid && !text_loss` 的块，而不是按文件是否存在判断。缓存迁移时，旧记录先保留为只读历史，新版本生成新分桶；删除旧缓存只能在回放验证、磁盘与电量策略都允许时发生。

**最终版本表是 prompt 的工程交付物。** 每个版本至少记录：prompt 全文哈希、变更原因、适用模型、允许的 JSON schema、示例数、反例数、前因窗口、是否允许 post-cue、thinking 模式、max_tokens、重试规则、gate 规则、人工盲听结果和手机平均耗时。没有版本表，就无法判断“新 prompt 更会演戏”是不是牺牲了逐字保真，也无法安全回滚。review 成本数据可下载：[复核成本数据](/data/workspace/dr:31/data_review_cost.csv)。

## 8. 推荐落地的最小可行方案与分阶段验证

**第一版不要追求“全能导演 prompt”，而要追求失败可定位。** 系统部分固定四段：任务定义、逐字铁律、JSON 与长度规则、输出示例；用户部分按“活跃角色子集—紧邻前因—目标块—最近 3 条历史”的顺序排列，禁用目标段之后的整段原文。生成时关闭思考，使用固定低温度与合理 max_tokens；输出先过 GBNF，再解析，再做字符级覆盖检查。第一次失败只重试一次，输入保持不变或仅改变解析/长度策略；仍失败则直读并写事件。这个方案直接回应项目现状：缺 few-shot、缺反例、缺分层，也没有利用“角色表小、任务固定”的端侧优势。

**第二版应把切分、校验、生成和合成拆成四个可替换单元。** 确定性代码产生原文行、归一化文本和字符偏移；4B 只预测 `speaker`、少量受控标签和短 instruct；程序组装 TTS 请求；TTS 接收全局 voice profile、逐行 direction 和可选同步标记。这样的边界意味着 prompt 变更很少直接破坏音频层：除非新增语义字段，TTS 层无需重训或重建；反之，只改 VoiceDesign 描述不应触发文本重标。

**第三版再做条件化 review，而不是默认两轮。** 高风险块使用更宽的上下文或更大模型；低风险块只走规则。可以用“是否跨引号块、角色表是否存在歧义、规则冲突数、字符损失、instruct 词表命中率”训练一个轻量路由，但在没有足够样本前，规则阈值比 ML 路由更可解释。若端侧无法承受额外调用，宁可把高损失块降为直读，也不要在 CPU 上重复整块推理。

**没有量化结论的部分必须明确等待真机实验。** 本次研究没有找到 Alexandria 的完整一手实现，也没有公开资料证明 five-fix 在 4B 中文小说逐块任务上的准确率、召回率或端侧耗时；同样，Qwen3-TTS 1.7B VoiceDesign 的逐行指令继承、本地 GGUF 参数和 JSON 标签能力仍需用具体模型卡与推理代码核实。报告中的 prompt 结构与成本判断属于基于证据的设计建议，不是云端方案替代；上线前应在目标 Android 机型、目标权重、目标 GGUF 量化与真实小说语料上测量字符级损失、说话人准确率、JSON 通过率、音频质量、prefill 与 decode 耗时、内存和电量。
