## 一、真机日志把上一轮的争论定案了

用户上一轮说「文本模型完全没在发力，甚至帮倒忙」「不标注合成效果也不错」。这次日志给出硬证据：

```
16:23 左右   块 1/2 开始（ANN_WAIT 一直报到 600s）
16:29:56.709 NATIVE_PREFILL_DONE tokens=979 nCtx=4096 nBatch=4096
16:29:57     NATIVE_DECODE_BEGIN
16:30:37.839 NATIVE_DECODE_FAIL llama_decode 返回非 0（紧接用户点了停止）
16:30:37.845 ANN_BLOCK_END 块 1/2 结束 · 0 条标注 · 通过 · 耗时 643428ms
16:32:25     PRODUCE_MODE 直接朗读（不过语言模型）
16:32:25     DIRECT_READ 2 块跳过标注，切成 8 段直接朗读
16:32:34     TTS_INPUT 段 1/8 textChars=88 → 16:36:03 段 2/8（单段约 3.5 分钟）
```

**结论（不绕）**：

- 标注档跑了 **10 分 43 秒，0 条标注**。不是「标得不准」，是**根本没产出可用标注**。
- 更糟的是日志把这次写成「**通过**」——`result` 为空时旧文案照样走 `else -> "通过"`，把白跑伪装成成功。日志骗人比跑得慢更严重。
- 所以用户听到的「不标注也不错」其实是 **A vs A**：标注档一旦 gate 不过就整块降级直读，和直接朗读喂给 TTS 的东西几乎一样。**真正被 4B 标成功的块，一次都没听到过。**
- 但据此**不能**判「标注本身没价值」，只能判「这一版这套标注在这台真机上没生效」。要判价值得跑「程序切句 + 模型只写短指令」的对照，那是后面的路线（B 方案），这轮不做。

**据此改的产品默认值**：新书默认「直接朗读」；标注档在界面明确标「实验性：真机上曾 10 分钟只产出 0 条标注」。已有任务按书签原样恢复，不擅自改用户正在跑的档。

## 二、断句：拿三个现成件拼，不手搓

旧实现（`Pipeline.Annotator.directSegments`）：

```kotlin
if (buf.length >= 110 || (buf.length >= 60 && boundary)) { ... }
```

**110 字是硬上限，不管是不是句子中间**——正是用户说的「按字符段」。真机 `TTS_INPUT` 里段 1 结尾「冷风就 →」、段 2 开头 `⏎⏎钟停在五点四十` 就是这个形状。

新文件 `core/TextSplitter.kt`，逐条对照现成源码：

| 抄谁 | 抄什么 | 落到哪 |
|---|---|---|
| Antioch `src/script/chunker.rs`（MIT） | `split_into_segments` 先按段落再按句；`is_heading_like` 短标题单独成段不与正文连读；`split_sentences` 边界判据 | 一级切点、标题段、中文标点集适配 |
| ReaderVoice-Mobile `SemanticSegmenter.kt` | 引号栈 + `source-exact` 区间切片：不在引号中间断、切片拼回去逐字无损 | `quoteDepth`、`substring` 不 trim |
| ensemble-reads `SegmentMerger.kt`（Apache-2.0） | 相邻单元合并到 `MAX_SEG_CHARS`；注释「单段本身超过上限的长独白保留原样，避免切碎语义」 | **没有字符硬切**，超长整句保留 |

规则：

1. 一级断点：句末 `。！？!?；;…` 且引号栈为空；或 `\n\n` 段落边界。切点落在**下一个实字**，空白留在前段尾部 ⇒ 拼回去逐字相等。
2. 二级断点：一级单元 > 260 字时，按 `，、,：:` 再断一次，**仍只按符号**。
3. 合并到 110 字目标：**只在单元边界合并**，标题单独成段。
4. **永不按字符硬切**；没有标点的长句整段保留，`oversize` 计数进日志。

`SPLIT_STATS` 事件给出：段数 / 句段边界 / 次级边界 / **字符硬切 0** / 超长整句保留 / 最长段 / 原文与拼回字数（逐字无损）。贴一段日志就能核对有没有从中间断。

## 三、作用域分层：长期默认 vs 仅本次

用户原话「哪些是长期有效的模型设置，哪些是仅这一轮任务的设置，没分开」。

**设置页 = 长期默认**（改一次写回 `Prefs`，对所有书生效），按模型分成两组：

| 组 | 包含 | 归属 |
|---|---|---|
| 模型文件 | 三个 GGUF 导入 / 查看 | 两个模型共用 |
| ① 语言模型 | 思考过程、上下文窗口、运算线程、随机度 | 只影响文字怎么被理解 |
| ② 音频模型 | 拟声表达、音色描述、角色映射、9 个采样参数、试音 | 只影响声音怎么发出来 |

「推理参数」卡原先夹在「声音」和「音频调试」中间，本轮**物理挪到 ① 组**；设置页顶部加「作用域」卡写明两页的区别。

**制作准备页 = 仅本次**（`ProduceConfig`，不写回 `Prefs`，随任务书签落盘）：

- ① 做什么 · 仅本次：制作方式、选章
- ② 怎么读 · 仅本次：朗读档位、语速倾向、情绪强度
- ③ 怎么跑 · 仅本次：段间静音、失败重做
- ④ 高级 · 跨书默认值（只读）：上下文 / 线程 / 随机度，去设置页改

底部文案改成「①②③ 仅本次、不写回设置；④ 是跨书长期默认值」。思考档仍不做本次级覆盖——它参与缓存分桶，两套真值会把续跑搞串。

## 四、日志模块本轮的四处修正

| 事件 | 改动 |
|---|---|
| `ANN_BLOCK_END` | 零产出 / 无结果 / 用户中断一律写 `WARN` 与真实状态，**不许写「通过」**；结构化字段带 `annCount` / `status` |
| `SPLIT_STATS` | 新增：断句是否按符号、有没有硬切、原文有没有少字 |
| `ANN_PHASE_HINT` | 新增：开工说明「先 prefill 好几分钟、再逐 token，期间块进度不动不是死机」 |
| `EXTERNAL_IMPORT_EMPTY` | 冷启动 `ACTION_MAIN` 不再被当成「收到分享但没拿到 Uri」写进 `CRASH`；只有 VIEW/EDIT/SEND 才推 incoming |

`NATIVE_DECODE_FAIL` 那条是 native 在用户停止后记的，本轮**不改 C++**（避免重编原生引擎），由 `ANN_BLOCK_END` 写「用户中断」覆盖解释。

## 六、研究落到设计上的两条判断

1. **两个模型怎么配合（读进上下文后定案）**：`voice_design` 权重吃的是 `text + instruct + lang=chinese`，`speaker` 必须传 null（传了被引擎判 `MODE_INVALID`）；它不挑角色、不挑音色，输入给什么演什么。4B 理论上只负责「谁说的 / 此刻怎么说」，音色身份由全局描述钉住。**但在这台 8Gen3 上，979 token 的 prefill 就要约 600 秒，4B 的成本远大于收益**——所以默认直接朗读是性能结论，不是审美结论。
2. **日志里那句「甜美娇喘女声。」是用户自己填的全局音色**，和后面「整体保持平稳叙述的节奏」直接打架：身份层要娇喘、情绪层要平稳，VoiceDesign 每次合成还会重新采样。建议换中性身份描述（如「沉稳的青年男声，中低音，吐字清晰」）。**不擅自改用户设置**，只登记。
